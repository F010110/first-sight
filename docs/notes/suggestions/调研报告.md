
# First-Sight 游戏环境选型与三摄数据采集技术调研报告

**项目：** First-Sight（旁白）
**研究对象：** Garry's Mod、inZOI
**调研日期：** 2026 年 10 月 29 日
**任务性质：** 技术可行性验证与最小原型开发

---

## 1. 项目背景及目标

First-Sight 是一个面向视障人群的长期生活辅助 Agent 项目。系统通过佩戴在用户头部的三个摄像头观察环境，建立长期空间记忆，回答与位置、物品、人物、历史活动和空间关系有关的问题。

当前需要建立一个高质量、可控制、可复现的 3D 虚拟生活环境，用于自动生成研究样本，并测试长期视觉记忆算法。

### 1.1 理想环境

希望拥有一个接近现代小城市的 3D 世界，满足：

1. 人类玩家能够自由控制角色行动。
2. 有住宅、道路、商店、多楼层建筑、楼梯等空间。
3. 可以执行完整的一天生活，包括起床、离家、购物、返回住宅、移动和存放物品。
4. 游戏具有较高视觉真实性，尽量接近正常 3D 游戏。
5. 世界状态具有持久性，同一物品在不同时间的位置可以变化并被记录。
6. 可以通过游戏脚本或源码控制世界，批量生成样本。

不要求完整模拟真实人体动作，也不要求复杂的机器人抓取物理。通过交互键完成物品移动是可以接受的。

### 1.2 核心技术要求

**A. 三摄视觉采集（最高优先级）**

需要以玩家头部为参考坐标系，固定三个摄像机：

- Front：朝向正前方
- Left：相对前方偏航 -90°
- Right：相对前方偏航 +90°

具体角度、FOV、分辨率和相机位置应当可以配置，以模拟真实头戴设备。

最低要求为 640×480 RGB、每路 0.5 FPS。后续希望支持更高分辨率和采样频率。

不一定要求真正并行渲染。允许在同一仿真状态下顺序渲染三个视角，但必须保证三路图像的世界状态一致。

必须能够自动获取三张图像的实际像素数据，而不仅是把三个画面显示在屏幕上。

**B. 位姿与 IMU**

需要输出：

- 玩家或头盔的三维位置
- 三维姿态（旋转矩阵或四元数）
- 三个相机的独立外参
- 时间戳
- 最好还能得到速度和角速度

基于真实位姿轨迹，进一步生成模拟 IMU：

- 三轴加速度计
- 三轴陀螺仪
- 可选磁力计
- 可配置偏置、噪声和漂移

应分别保存理想位姿真值与模拟传感器测量，避免评测时发生真值泄漏。

**C. 世界状态与事件记录**

希望能够读取：

- 物品 ID、位置、姿态和状态
- 玩家与物品的交互事件
- 进入和离开的区域
- 时间、天气、场景变化
- 有条件时读取 NPC 的位置和行为

这些信息用于自动生成长期记忆问题及答案。

## 2. 候选游戏一：Garry's Mod

### 2.1 基本信息

- 游戏类型：第一人称 3D 沙盒
- 引擎：Valve Source
- 游戏本体：商业软件
- 可编程接口：Lua
- 源码状态：游戏 Lua 层公开，完整引擎不开放
- 内容生态：Steam Workshop 中存在大量城市、住宅和 RP 地图

官方开发文档：

https://wiki.facepunch.com/gmod/

Lua 游戏逻辑：

https://github.com/Facepunch/garrysmod

### 2.2 已确认的摄像机能力

官方公开以下接口：

**render.RenderView(viewData)**

从指定位置、角度和 FOV 渲染场景。

https://wiki.facepunch.com/gmod/render.RenderView

**render.PushRenderTarget(texture)**

切换到自定义渲染目标。

https://wiki.facepunch.com/gmod/render.PushRenderTarget

**render.Capture(captureData)**

捕获当前渲染目标，返回图像二进制内容，可用于保存 JPEG 或 PNG。

https://wiki.facepunch.com/gmod/render.Capture

这三个接口已经构成三视角数据采集的主要技术基础。

但是尚未进行实际运行验证，不能直接认定稳定的三摄录制已经实现。

### 2.3 推荐的三摄方案

编写一个客户端 Lua Addon。

在每个采样时刻：

1. 读取玩家眼部或虚拟头盔的位姿。
2. 根据固定的相机外参，计算三个视角的位置和朝向。
3. 将同一仿真状态关联到一个采样编号。
4. 创建或复用 RenderTarget。
5. 分别调用 render.RenderView 渲染三个视角。
6. 使用 render.Capture 得到图像二进制。
7. 保存 front.jpg、left.jpg、right.jpg。
8. 保存全部相机参数和玩家位姿。

应当优先尝试在同一个渲染回调中完成三路采集，而不是通过修改玩家视角、等待多个游戏帧来截图。

### 2.4 需要验证的技术风险

**风险 G1：RenderView 的已知渲染问题**

官方文档指出，静态物体和 LOD 可能因为距离判断错误而显示异常。

需要检查三个方向的建筑、家具、远景是否正常。

**风险 G2：RenderTarget 捕获限制**

render.Capture 需要在适当的渲染回调中执行，否则可能得到黑色图像。

还需要检查图像是否上下翻转、透明、尺寸错误，或者捕获到了错误的纹理。

**风险 G3：同一帧多次渲染的稳定性**

需要确认三次 render.RenderView：

- 是否互相影响
- 是否导致材质或光照异常
- 是否存在动态物体渲染不一致
- 是否能够保证游戏世界只更新一次

不应仅根据三张图片生成成功就宣布三摄同步验证成功。

**风险 G4：游戏性能**

三次渲染可能显著增加 GPU 负担。对于离线数据生成，可以接受低于实时速度的运行方式。

### 2.5 位姿和 IMU

官方存在以下接口：

- Entity:GetPos()
- Entity:GetAngles()
- Entity:GetVelocity()
- Player:EyeAngles()
- Entity:GetBoneMatrix()
- PhysObj:GetAngleVelocity()

玩家的位置、视角等可以读取，但要注意实体角度、眼部角度和骨骼角度未必一致。

建议统一定义 HeadPose，然后据此计算全部传感器外参。

Source 引擎的世界单位通常需要按约定换算为米。应明确单位尺度、坐标轴方向及旋转约定，必要时使用地图内已知尺寸物体校准。

IMU 需要由连续真实位姿生成，不能直接将游戏位置当作 IMU 测量值。

特别需要验证姿态采样频率、时间戳精度与游戏 tick 频率之间的关系。

### 2.6 生活模拟能力

Garry's Mod 原生支持自由行走、上下楼、物理物品操作等，但不自带完整的普通人生活模拟流程。

需要寻找合适的城市 Roleplay 地图或 Addon 组合。

请重点寻找：

- 现代城市或小镇地图
- 可进入的多层住宅
- 可进入的商店、办公楼和公共建筑
- 可以拾起、携带、放下的物品
- 可以保存并恢复的物品位置
- 无须依赖公共服务器即可运行的本地模式

地图和 Workshop 资源的许可证应分别核查。

**初步评价：Garry's Mod 的三摄接口证据较强，生活模拟能力依赖地图和插件。**

## 3. 候选游戏二：inZOI

### 3.1 基本信息

- 游戏类型：现代城市生活模拟
- 引擎：Unreal Engine 5
- 游戏本体：商业软件
- 官方扩展：ModKit、Lua API
- 游戏源码：未公开完整源码
- 可编程控制：存在官方 Mod API 和相关自动化工具

官方文档：

https://mod-docs.playinzoi.com/

### 3.2 生活环境优势

inZOI 相较 Garry's Mod 更接近我们希望模拟的生活内容：

- 现代城市环境
- 住宅与家具
- 人物生活活动
- 物品和家具交互
- 日常活动与作息
- 昼夜与环境变化

但应当核实：

- 是否可以自由第一人称行走
- 是否能够跨住宅、商店、街道连续活动
- 建筑内部是否可以自由探索
- 生活物品是否能被任意搬动、放下
- 物品状态能否由脚本读取和恢复
- 游戏是否存在无法绕开的场景切换或控制限制

不能把游戏的视觉生活模拟能力直接等同于可编程采样能力。

### 3.3 关键发现：AB1SceneCapture2D

官方文档：

https://mod-docs.playinzoi.com/docs/modkit-docs/wiki/luaapi/b1/classes/ab1scenecapture2d/

这个类属于 B1 Presentation 环境，继承 Unreal Engine 的 ASceneCapture2D。

文档列出：

**属性**

- AttachBoneName
- Offset
- CaptureOption
- SceneCaptureTarget
- SceneCaptureMaterial
- DebugCamera

**函数**

- CaptureScene(...)
- OnCaptureScene(...)
- SetSceneCaptureTarget(...)

这些接口表明，游戏内部具有通过额外相机捕获场景的机制。

但关键问题尚未解决。

**需要确认普通 Lua Mod 是否可以创建 AB1SceneCapture2D 实例，以及是否可以读取其渲染输出的 RGB 像素。**

这两个条件比函数名称本身重要得多。

### 3.4 B1 / B2 环境限制

inZOI 官方 Lua API：

https://mod-docs.playinzoi.com/docs/modkit-docs/wiki/luaapi/

根据官方文档：

- B2 Simulation 主要负责仿真逻辑。
- B1 Presentation 涉及表现层、特效、摄像机。
- Lua Mod 主要运行在 B2 线程。

因此，需要重点调查 B2 Mod 对 B1 摄像机对象的访问权限。

具体问题：

1. B2 脚本能否创建 B1 SceneCapture Actor？
2. 有没有现成的跨 B1/B2 调用方式？
3. 是否存在无法访问的引擎类型或受限函数？
4. 是否支持动态创建 RenderTarget？
5. CaptureScene 得到的材质能否被读取或保存？
6. 是否有官方截图或纹理编码接口？
7. 能否在同一仿真状态下进行三次捕获？

如果普通 Mod 无法访问这些能力，需要评估其他公开扩展方式，但不应直接转向大规模逆向工程。

### 3.5 第一人称模式及相关 Mod

此前调研发现 inZOI 已有第一人称功能，以及社区对人物跟随摄像机的修改。

需要进一步核实这些功能具体调用哪些 API。

这可能解决以下环节：

- 摄像机绑定头部
- 控制摄像机偏航
- 获取相机位置
- 调整 FOV

但是第一人称 Mod 并不等于三摄采集 Mod。

它可能只是在修改玩家的主摄像机，无法创建额外的相机或导出独立图像。

### 3.6 三摄实现的两条路径

**方案 I：三个 SceneCapture2D**

如果普通 Mod 可以创建额外 SceneCapture：

1. 创建三个相机。
2. 绑定人物头部或虚拟头盔。
3. 配置相对外参。
4. 创建三个 RenderTarget。
5. 在同一仿真状态下调用捕获。
6. 导出三个 RenderTarget 的 RGB。
7. 保存位姿与时间戳。

这是首选实现方式。

**方案 II：主摄像机顺序切换**

如果不能创建三个 SceneCapture：

1. 冻结或暂停仿真状态。
2. 调整主摄像机为前摄。
3. 渲染并截图。
4. 调整为左摄，截图。
5. 调整为右摄，截图。
6. 恢复相机和仿真。

必须验证暂停期间摄像机能否正常更新，以及导出的三张图像是否严格对应同一世界状态。

如果仅能手工截图而无法通过脚本控制，则不符合自动样本生成器的要求。

### 3.7 位姿与 IMU

inZOI 使用 Unreal Engine，内部具备三维变换、动画和物理仿真的基础能力。

但是我们需要通过实际 Mod API 取得：

- 角色世界坐标
- 头部骨骼或相机位姿
- 旋转矩阵或四元数
- 连续运动轨迹
- 稳定的时间戳

不能仅根据 UE5 本身支持相关功能，就认为 inZOI 已向普通 Mod 开放了这些接口。

若能够稳定获得位姿序列，可离线生成模拟 IMU。

### 3.8 初步评价

inZOI 在现代生活场景、人物行为、视觉真实性方面有明显优势。

但其三摄采集仍存在两个关键未知：

- 是否允许创建和控制独立场景摄像机。
- 是否允许导出其原始 RGB 图像。

**在这两个问题得到实际验证之前，不应将 inZOI 确定为 First-Sight 的正式模拟环境。**

## 4. 两款游戏的技术对比

| 需求             | Garry's Mod        | inZOI                 |
| ---------------- | ------------------ | --------------------- |
| 现代生活场景     | 需要社区地图       | 游戏核心内容          |
| 完整城市生活     | 需要扩展           | 更接近目标            |
| 第一人称自由移动 | 原生支持           | 需验证实际控制方式    |
| 自定义镜头位姿   | 官方 Lua API       | 有相关接口            |
| 渲染额外视角     | RenderView         | SceneCapture2D 底层类 |
| 图像数据读取     | Capture API 已公开 | 未确认                |
| 三摄同步采集     | 需要原型验证       | 需要原型验证          |
| 位姿真值         | API 较明确         | 待核实                |
| 模拟 IMU         | 可通过位姿计算     | 取决于位姿读取        |
| 源码控制         | Lua 层             | Mod 层                |
| 公开数据授权     | 需核查游戏和地图   | 需核查游戏协议        |

总体判断：

**Garry's Mod 技术实现风险较低，inZOI 生活场景质量较高。**

不能因为 inZOI 使用 Unreal Engine 就认定其三摄容易实现，也不能因为 Garry's Mod 的渲染 API 完整就认定它已能模拟正常人的一天。

## 5. Agent 实际验证任务

请从信息调研进入动手验证阶段。优先使用官方接口，不进行未经授权的逆向破解。

### 阶段 A：环境及接口确认

对于两个游戏分别完成：

1. 核实游戏实际安装状态、版本、Mod 环境及依赖。
2. 阅读官方 API 文档，确认相关接口可在当前版本调用。
3. 检查已有的开源采集 Mod 或摄像机 Mod。
4. 明确代码能够修改到哪一层。
5. 识别需要游戏本体或用户登录的步骤。

如果游戏尚未安装，先完成不依赖运行游戏的源码和文档验证，不要将它描述为已完成实测。

### 阶段 B：三摄最小原型

这是最高优先级。

**测试 B1：静态三摄**

在同一静态场景中导出：

- front.png
- left.png
- right.png
- camera_pose.json

要求三张图片视角明显不同，分辨率正确，能够正常读取。

**测试 B2：动态三摄**

玩家移动 60 秒，尝试每两秒采集一次。

目标输出 30 组三摄数据，并检查：

- 是否丢帧
- 是否出现黑图
- 是否出现相机方向错误
- 是否出现明显画面不同步
- 是否影响玩家移动
- 是否能恢复原本的游戏渲染状态

**测试 B3：位姿输出**

每个采样时刻保存：

- HeadPose
- FrontCameraPose
- LeftCameraPose
- RightCameraPose
- Timestamp

确保摄像机相对头部的外参稳定。

### 阶段 C：IMU 数据验证

尝试记录连续位姿序列，计算线速度、角速度和加速度。

优先确保真值轨迹正确，而不是立即加入复杂的噪声模型。

输出独立的轨迹文件，并提供一个 Python 脚本，从轨迹生成含噪声的模拟 IMU 数据。

测试静止、直线移动、转弯和上下楼四种情况。

如果运动轨迹采样率不足，应明确实际时间分辨率，不得把插值采样等同于物理引擎原生的高频 IMU。

### 阶段 D：生活任务验证

在三摄功能基本验证后，测试一个最小生活流程：

1. 从住宅二楼出发。
2. 走下楼梯。
3. 离开住宅，进入街道。
4. 进入另一栋建筑。
5. 移动一个可交互物品。
6. 离开后返回。
7. 检查物品位置是否保留。
8. 获取这一流程的图像、轨迹与状态标注。

在能够完成这个流程之前，不应声称游戏已经满足完整的一天生活模拟。

## 6. 建议的数据格式

建议采用如下目录结构：

```text
first_sight_dataset/
  episode_0001/
    metadata.json
    trajectory.jsonl
    world_events.jsonl
    cameras/
      front/
        000001.jpg
      left/
        000001.jpg
      right/
        000001.jpg
    sensors/
      imu.csv
```

每一组图像应有统一采样编号。

`trajectory.jsonl` 至少包含：

```json
{
  "sample_id": 1,
  "sim_time_s": 2.0,
  "head_position_m": [1.0, 2.0, 1.6],
  "head_quaternion_xyzw": [0, 0, 0, 1],
  "camera_frames": {
    "front": "cameras/front/000001.jpg",
    "left": "cameras/left/000001.jpg",
    "right": "cameras/right/000001.jpg"
  }
}
```

以上数据仅为格式示例，不代表真实采集值。

正式格式必须另外记录坐标系定义、相机内参、外参、单位换算、游戏版本、地图版本和采集配置。

世界真值仅用于生成标签及评测，不允许直接输入被评测的空间记忆系统。

## 7. 成功标准与止损条件

### 三摄验证成功

至少达到：

- 在正常游戏过程中自动采集三路不同视角。
- 三路视角对应一致的世界状态。
- 三路图像具有可重现的相机参数。
- 不依赖人工逐张截图。
- 可获得完整位姿与时间戳。
- 连续采集 30 组以上，不出现严重错误。

此标准通过后，可以启动规模化样本生成开发。

### 需要暂停的情况

如果出现以下问题，应及时停止该技术路线并提交分析：

- 普通 Mod 无法读取独立摄像机像素。
- 必须修改无法取得的闭源引擎。
- 只能通过不可控的手工截图获取图像。
- 无法稳定取得采样时刻的位姿。
- 场景结构无法满足基础跨建筑生活任务。
- 公开科研使用或数据分发存在无法接受的授权限制。

不要求所有功能一次性实现，但必须清楚标注哪些已实现、哪些仅在理论上可行。

## 8. 最终需要 Agent 提交的成果

请分别为 Garry's Mod 和 inZOI 输出：

1. **已验证能力**：有实际测试结果的功能。
2. **文档确认能力**：官方 API 支持，但尚未运行的功能。
3. **不可确认功能**：文档和实测尚无法证明的功能。
4. **源码与代码修改方式**：具体文件、目录、插件入口和依赖。
5. **最小原型代码**：能够实际运行的三摄采集实现。
6. **运行方式**：安装、启动、采集和导出步骤。
7. **测试产物**：三摄样张、位姿数据、日志和错误记录。
8. **授权风险**：游戏本体、地图、模型与图像数据的使用边界。
9. **技术结论**：能否成为 First-Sight 的长期生活数据生成器。

请避免仅凭 Unreal Engine 或 Source Engine 的通用能力推断具体游戏的接口可用性。

**本次任务的最终目标不是完成整个 First-Sight 模拟器，而是用可复现的实际证据，确定哪款游戏能够稳定生成三摄图像、位姿和基础生活轨迹。**

优先级：

**三摄图像导出 → 位姿真值 → 模拟 IMU → 生活场景 → 完整长期数据集。**

只有确认前两个核心环节成功后，才需要投入较大精力开发完整生活模拟系统。
