
我觉得完全可以做，而且你们不需要等三摄头盔到手，也不需要从零搭建一栋大楼。

更重要的是，我查到了一个与你们当前阶段非常接近的新基准：MeMoREval（2026年10月8日）。它专门研究具身智能体在经历一段环境观察之后，究竟应该保存什么记忆、如何利用记忆完成后续任务，并同时衡量记忆构建和使用成本。

这说明你们现在要做的事情已经有很明确的研究方向，不必自己凭空发明评测任务。

我建议分成两个层次：

1. 先在现成的大型3D建筑中生成多次探索的三摄像头数据，验证长期空间记忆。
2. 再将场景、轨迹和任务组织成可复现的长期记忆 Benchmark。

第一步可以很快形成软件闭环，第二步才是可能有科研价值的部分。

其中 HM3DSEM 值得特别指出：它包含216个带语义标注的建筑级场景、约3,100个房间。对你们来说，这比单纯找到1,000张漂亮的建筑地图更重要，因为它提供了可用于评测的空间标签。

[HM3DSEM论文](https://arxiv.org/abs/2210.05633)

## 三、我建议直接定义一个长期空间记忆Benchmark

暂时叫它 Long-Horizon Spatial Memory Benchmark。

你们不需要等真的运行几天才能测试长期记忆。

“长期”在Benchmark中首先意味着跨多个独立探索会话、跨时间保存并复用信息，而不是要求视频必须连续录制72小时。

例如在同一建筑生成五次探索：

一个建筑的五次探索协议

1. Session 1：初次探索

   从入口进入，访问部分房间，建立初始区域图和历史路径
2. Session 2：换一条路线

   从另一个入口探索，与之前部分区域重叠，测试同一区域重访识别
3. Session 3：相似区域干扰

   访问结构相近的房间、走廊、不同楼层，测试错误合并
4. Session 4：环境变化

   移动可编辑场景中的物体、改变门状态，测试旧记忆是否过时
5. Session 5：记忆驱动任务

   只允许访问前四次探索积累的长期记忆，再根据历史信息检索或导航

注意，Session 4的环境变化在ProcTHOR这类可编辑场景中更容易做；不能默认HM3D静态扫描能随意改变墙体、楼层和所有家具。

### 模拟器中给Agent哪些信息？

只给：

\\[ O_t=(I_t^{front},I_t^{left},I_t^{right}) \\]

外加你们产品实际拥有的时间戳、动作事件（如果有）。

不要给Agent真实位姿、真实房间ID或者全局地图。

但模拟器内部要保留这些数据作为评测真值：

\\[ GT_t=(x_t,y_t,z_t,\theta_t,r_t) \\]

这样才能客观判断机器人是否重访同一地点，以及记忆里的区域节点是否正确。

这就是仿真的巨大优势：算法不使用真值，但评测器可以使用真值。

## 四、Benchmark的目标不能只有“房间识别准确率”

这是我觉得你们最应该改变的地方。

空间识别已经有不错的VLM基线。如果新的Benchmark还只测某张图片属于哪个房间，很容易再次变成VLM能力测试。

我建议拆成四项任务。

| 任务                 | 具体测试                                   | 核心指标                             |
| -------------------- | ------------------------------------------ | ------------------------------------ |
| 长期区域身份         | 多次进入同一房间，是否始终关联同一个区域ID | Revisit Accuracy、误合并率、误拆分率 |
| 历史空间检索         | “上一次在哪里看见那张红色沙发？”         | Retrieval Recall\@K、回答正确率      |
| 历史路径复用         | “从当前大厅到昨天去过的会议室。”         | 导航成功率、路径效率                 |
| 环境变化后的记忆更新 | 原来的物体移动、门不可通行，是否更新旧记忆 | 更新准确率、过时记忆使用率           |

我尤其推荐第三项。

因为你们之前设想的拓扑边保存历史移动路径终于能够发挥实际作用。

假设机器人第一次经过：

\\[ A\rightarrow B\rightarrow C\rightarrow D \\]

下一次在A收到任务：

> 返回之前的D。

长期记忆系统应该提供可复用的历史路线，而不是让VLM从当前画面重新猜测D在哪里。

这就能测量：

有记忆时，相比重新探索，究竟节省了多少路径长度、时间和VLM调用成本？

这才是真正对产品有意义的Benchmark。

如果暂时没有实现导航控制，也可以先做离线记忆检索任务，再逐渐升级到闭环导航。两者应当分别报告，不要把检索成功等同于导航成功。

## 五、现成的长期记忆Benchmark其实已经出现了

这一点很重要，因为你们甚至不需要从零定义全部任务。

[MeMoREval — What Should Embodied Agents Remember?](https://arxiv.org/abs/2610.12561)

Wang et al., 2026年10月8日

在4个模拟室内环境中提供53项任务，采用“先经历环境，再提出记忆任务”的协议，并测量记忆构建和使用成本。论文发现，保存原始图像相比只存文本描述有明显价值，而图像与场景图联合存储表现更强。

这篇尤其贴合你们的VLM调用预算与长期记忆设计问题。

[FindingDory: A Benchmark to Evaluate Memory in Embodied Agents](https://arxiv.org/abs/2506.15635)

Yadav et al., 2025

基于Habitat，包含60项面向长期记忆的具身任务，不仅测历史信息回忆，还关注根据记忆实际执行导航和交互动作。

很适合作为你们的任务协议参考。

[EvoNav-Bench: Benchmarking Lifelong Navigation in Evolving Environments](https://arxiv.org/abs/2609.08292)

Wang et al., 2026

基于ProcTHOR，在连续导航任务之间主动修改环境，专门测试智能体能否适应过时的历史记忆。

适合作为你们第二阶段的动态环境Benchmark参考。

这三篇已经将长期记忆的三个关键维度组织得比较清楚：

\\[ \boxed{ \text{记住什么} \quad+\quad \text{怎样利用} \quad+\quad \text{何时更新} } \\]

你们完全可以借鉴它们的任务形式，再加入自己的三摄像头观测和房间拓扑表示。

## 六、我会怎样搭建第一版数据生成器？

不需要一开始就写复杂的Agent控制框架。

先做一个可确定性回放的数据生成器：

```
Simulator
 ├── Scene Loader
 │    ├── HM3DSEM / MP3D
 │    └── HSSD
 │
 ├── Agent Controller
 │    ├── 轨迹采样
 │    ├── 重访路线生成
 │    └── 多Session调度
 │
 ├── Three-Camera Renderer
 │    ├── Front RGB
 │    ├── Left RGB
 │    └── Right RGB
 │
 ├── Ground Truth Recorder
 │    ├── 真实位姿
 │    ├── 真实区域ID
 │    ├── 房间连接关系
 │    └── 实际历史路径
 │
 └── Benchmark Exporter
      ├── 观测数据
      ├── Session信息
      ├── 任务与问题
      └── 评测真值
```

### 三摄像头怎么模拟？

在同一个智能体上放置三个RGB虚拟相机：

\\[ \theta_F=0^\circ \\]

\\[ \theta_L=-90^\circ \\]

\\[ \theta_R=+90^\circ \\]

三个相机的朝向固定，使用相同的仿真时间戳。

如果实际头盔的相机存在位置偏移、俯仰角或视场角差异，就在硬件到手后更新参数。早期不必要求完全一致。

第一版每条观测可以采用类似格式：

```
{
  "session_id": "visit_03",
  "timestamp": 128.5,
  "cameras": {
    "front": "front_01285.jpg",
    "left": "left_01285.jpg",
    "right": "right_01285.jpg"
  },
  "evaluation_only": {
    "room_id": "floor_2_room_17",
    "pose": [12.4, 1.7, -3.2, 0.82]
  }
}
```

`evaluation_only`字段必须与Agent的运行输入严格隔离。

我建议保存较高频率的原始观察，但只按你们的实际策略抽样调用VLM。这样以后即使更换Prompt、VLM或采样频率，也不必重新渲染整套场景。

## 七、第一版Benchmark做到多大合适？

我不建议一开始就渲染上千栋建筑。

可以用一个可控的小规模试点，再扩充。

建议的第一版目标规模

建筑场景

# 10–20

每建筑独立探索

# 5次

探索会话总量

# 50–100

记忆任务目标

# 200–500

以上是建议的试点设计目标，并非已存在的数据集规模或完成结果。

数据集划分要按整栋建筑进行，不要将同一建筑的不同Session分别放在训练和测试集。

最初甚至只要选3栋建筑，确保数据生成、VLM记忆写入、记忆检索、评测器完整跑通，再扩展到上述规模。

## 八、Benchmark必须设置的对照实验

考虑到你们之前发现“VLM直接看全部图片”效果最好，我认为最强基线应该原封不动保留。

| Baseline | 记忆策略                           | 意义                             |
| -------- | ---------------------------------- | -------------------------------- |
| B0       | 仅当前三摄像头观察，不使用历史记忆 | 无记忆下限                       |
| B1       | 保存全部历史图像，直接给VLM        | 你们目前最强的暴力基线           |
| B2       | 固定时间抽样图像 + VLM             | 简单低成本基线                   |
| B3       | 每次观察生成文字摘要，长期保存文本 | 文本记忆基线                     |
| B4       | 图像检索 + VLM                     | 非结构化视觉长期记忆             |
| B5       | 图像检索 + 房间拓扑图 + 历史路径   | 你们的长期空间记忆方案           |
| Oracle   | 使用真实区域图辅助检索和规划       | 理论参考上界，不算真实可部署方法 |

这里有一个实验陷阱需要避免：

不能因为B1看了10,000张历史图片，而B5只检索了20张，就直接宣称两者在同等条件下谁更好。

需要同时报告：

- 任务成功率。
- VLM输入Token或图像成本。
- 总调用次数。
- 推理延迟。
- 持久化存储量。

最好绘制一条任务成功率—总推理成本曲线。

因为在你们目前的产品条件下，长期记忆模块最可能带来的优势，不一定是比全量VLM更聪明，而是：

> 用远少于全量历史的输入，达到接近全量历史的空间任务表现，并能够跨多个Session持续工作。

这是一个很明确、可验证、具有产品价值的目标。

## 九、我认为最需要警惕的不是渲染质量，而是Benchmark设计错误

渲染质量当然影响VLM表现，尤其会影响小物体和语义识别。

但你们现在已经在HSSD观察到：更强的VLM上下文能够克服一部分复杂空间识别困难。

因此，我认为现阶段有三个问题比画质更优先。

第一，不能让任务被当前画面直接解决。

如果问题是“这里是客厅还是厨房”，那不是长期记忆任务。

任务必须依赖历史信息，例如：

“昨天在二楼看到的那把蓝色椅子，出现在哪个区域？”

第二，要区分房间级记忆与具体地点级记忆。

如果一条历史路径从一个大厅入口走到另一个出口，整个大厅只有一个节点可能不足以支持精确路线复用。

Benchmark应该允许你们发现这种表示不足，而不是预先假设一个房间节点可以解决所有导航任务。

第三，避免将房间边界的歧义作为唯一决定性评测。

你们已经在复杂建筑中遇到过人类都难以判断区域边界的问题。

这时可以同时提供物理区域标签和宽松的语义区域标签；争议位置单独标注，而不是强行把唯一正确答案交给人工主观判断。

## 十、我建议你们的执行顺序

1

先用当前HSSD环境跑通多Session接口。

不换模型、不动VLM房间识别算法，只把原本一次探索拆成多次独立访问。确认长期记忆跨Session持久化。

2

切换到HM3DSEM，选择结构复杂的建筑。

做跨房间、重复走廊、跨楼层和回访实验，生成三视角RGB与真值区域标签。

3

先完成离线长期记忆评测。

同一组历史观察输入不同记忆方案，比较检索、区域重访、历史路径问答与调用成本。

4

再引入MANSION或ProcTHOR，增加场景变化和闭环导航。

这一阶段重点测试过时记忆、路径失败后的修正，以及真正利用历史路线完成任务。

5

最后用真实三摄头盔做Sim-to-Real测试。

尽量沿用同一套数据协议和评测接口，只替换数据采集器。

## 最后，我对这个方向的科研判断反而更乐观了一点

此前你们反复在研究“怎样构造正确的房间分组”，最后发现直接让VLM观察完整信息往往更好。

但长期空间记忆面临的是另一个不可回避的问题：

当历史从几百张图片增加到几十万张，且跨越多个独立会话时，系统如何以有限预算保留、检索、修正和利用真正重要的空间经验？

MeMoREval、FindingDory 和 EvoNav-Bench 已经证明这是一个明确的研究方向，同时也意味着你们不能简单声称自己首次提出长期具身记忆。

我反而建议先把研究目标确定为：

在三视角RGB、无真实位姿输入的条件下，实现跨Session可持续的空间记忆，并评估其在重访、历史路线复用和动态环境中的任务性能与推理成本。

这既有产品意义，也有可复现的研究目标。

所以我现在会明确选择：Habitat-Sim + HM3DSEM 做主Benchmark，MANSION作为大型可编辑建筑的扩展；先生成标准化多Session数据，再讨论需要什么长期记忆算法。

这条路线完全不需要等你们的三摄头盔到手才开始。
