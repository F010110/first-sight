
我认为你现在确实应该暂停一部分架构上的自主探索，系统地研究已有在线 Agent 的实现。

而且这里需要修正我之前的判断：我不应该在没有仔细检查 First-Sight 代码的情况下，就默认你们需要一个简单的「前台感知＋后台记忆」架构。你们已经经历了大规模重构，当前实现可能比不少论文系统复杂，真正需要的是有针对性的架构对照，而不是再设计一套通用方案。

我查到了几套值得直接看代码的系统。最重要的发现是：有些工作不仅研究连续视频和长期记忆，还公开了 streaming harness、记忆维护模块和评测执行器。 这些比单纯阅读方法论文更适合你们现在的阶段。

## 一、最值得研究的五套开源实现

# 1

StreamArena / StreamMind

优先研究 Harness

2026 · 代码已公开

最贴近你们当前的实时调度问题。提供独立调度的前端任务、异步长期记忆构建、历史检索和主动监测，并公开 StreamingAgent 接口与流式评测驱动。

重点看 `method/streammind/`：前后台执行协调、记忆写入时机、请求处理，以及实时评测怎样真正运行。

# 2

DirectMe / UCS-Bench

优先研究空间记忆

ICML 2026 · 代码已公开

持续从第一视角视频构建结构化3D空间记忆，支持物体位置、场景图、时间戳约束检索及空间问答。

重点看 `directme/mapping/`、`storage/`、`retrieval/`，特别是场景图更新、持久化和查询时如何保持时间一致性。

但其公开代码包含 offline mapping engine，不能仅凭论文中的 continual/streaming 描述就认定它满足真实墙钟时间的实时运行要求。

[GitHub 仓库](https://github.com/cocowy1/UCS-Bench?utm_source=chatgpt.com) · [论文](https://proceedings.mlr.press/v306/wang26je.html?utm_source=chatgpt.com)

## 二、StreamMind 有一个值得立即借鉴的细节

我进一步检查了它的实现文档，发现它并不只是论文中的概念架构。

它公开了以下关键文件：

| 文件                     | 作用                                                                                      |
| ------------------------ | ----------------------------------------------------------------------------------------- |
| `agent_with_memory.py` | FrontWorker、MemoryWriter、RouterWorker、SearchWorker、RecallWorker，以及三层 SQLite 记忆 |
| `agent_monitor.py`     | 主动监测工作池                                                                            |
| `streammind_agent.py`  | 将原始 Agent 接入统一流式接口                                                             |
| `run_streammind.py`    | 按真实墙钟时间持续送帧，不因问答暂停视频                                                  |
| `agent.py`             | 统一 Agent 生命周期和异步事件接口                                                         |

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub

其中 `run_streammind.py` 特别值得你们研究。

它不是先处理完一帧再送下一帧，而是按时间调度输入，并异步触发 `on_frame`。即使 Agent 处理速度不够快，视频时间也继续前进。Agent 则通过独立接口提交结果。

这种评测机制能够直接揭露一些离线运行不会暴露的问题。

不过，异步派发不等于系统真的实现了实时性。我们仍需检查内部如何控制任务积压、写入竞争和状态版本；这些不能仅凭 README 得出结论。

## 三、怎么把这些实现真正用于 First-Sight？

我不建议让 Coding Agent 阅读五篇论文后，直接按其中一套架构重做项目。

你们此前已经发生过设计丢失和多次大规模重构。现在最需要避免的是让外部架构再次冲击现有系统。

我的建议是做一次限定范围的架构审计，先不修改代码。

具体审查以下六个问题：

| 审查项目 | 希望得到的结论                           |
| -------- | ---------------------------------------- |
| 数据流   | 从新帧输入到长期记忆提交，经过哪些组件   |
| 执行模型 | 哪些任务同步执行、哪些并行、哪些必须串行 |
| 状态归属 | 谁维护当前状态，谁有权更新长期状态       |
| 时间语义 | 如何处理旧观测、迟到结果与未来信息泄漏   |
| 过载策略 | 处理速度落后时如何保证系统不失控         |
| 回归机制 | 哪些自动测试能防止实时性再次被破坏       |

对于每一项，让 Agent 同时列出 First-Sight 的实现方式、参考系统的实现方式，以及双方各自的优势和缺陷。

重要的是保留你们已经完成的设计，而不是默认论文代码更先进。

事实上，科研代码经常只为某个实验协议优化，未必比你们现在的系统更适合持续运行。

## 四、建议直接交给 Coding Agent 的任务

对 First-Sight 当前的在线空间记忆 Agent 进行一次参考实现研究与架构审计。

**第一阶段：理解当前项目**

完整阅读项目核心设计文档以及实时执行、短期 Context、空间状态维护、长期记忆库相关代码。

重建系统实际的数据流、任务调度、状态更新及持久化过程。区分设计文档中的预期行为和代码实际行为。

**第二阶段：研究已有实现**

重点检查以下开源项目：

1. StreamArena / StreamMind[https://github.com/JIA-Lab-research/StreamArena](https://github.com/JIA-Lab-research/StreamArena)
2. DirectMe / UCS-Bench[https://github.com/cocowy1/UCS-Bench](https://github.com/cocowy1/UCS-Bench)
3. EventMemAgent
   [https://github.com/lingcco/EventMemAgent](https://github.com/lingcco/EventMemAgent)

必须阅读相关实现代码，不得只根据论文摘要或 README 推断其内部行为。

重点研究实时调度、异步任务、短期上下文、长期记忆写入、状态同步、积压处理和流式评测机制。

**第三阶段：对照分析**

逐项比较当前 First-Sight 与参考实现：

- 已经采用的相似机制
- 当前实现中更复杂或更完善的部分
- 可能存在的设计缺陷
- 值得借鉴但尚未实现的机制
- 不适合 First-Sight 需求的设计

每个关键判断必须提供具体文件、函数或代码位置作为依据。

**第四阶段：提出建议**

按照必要性、风险、改动规模排序。

优先考虑局部修复和可验证的改进，不默认采用参考项目的完整架构。

**严格要求**

本次任务只允许研究与输出报告，不得修改现有实现或核心设计文档。不得将某个论文方法的设计与其公开代码的实际能力混为一谈。

最终提供可供人类阅读的架构对照报告，并明确指出仍需人工决定的问题。

## 五、对科研前景的进一步判断

通过这次检索，我反而更倾向于认为，你们有必要先把工程系统和科研工作区分开来。

StreamMind 解决的是流式视频 Agent 的实时交互与长期记忆协调，DirectMe 研究的是持续第一视角空间记忆。它们的交集与你们的问题非常接近，但设计假设可能不同。

如果 First-Sight 最终能够实现一个兼顾持续在线处理、空间状态一致性、弱位姿输入和长期记忆的系统，确实可能产生科研贡献。

不过，是否足以写成论文，不能由架构复杂度决定，而需要通过实验说明现有方法哪里不足，以及你们的设计带来了什么改进。

我的明确建议是：这次先集中精力研究 StreamMind 和 DirectMe 两套代码。

前者回答「在线 Agent 怎么持续运行」，后者回答「持续空间记忆怎么组织」。这两件事正好对应你们目前最大的两个难点。

而且这次最好由你亲自参与架构对照报告的审阅。你不需要逐行读完所有代码，但必须知道当前系统为什么这样设计、哪些部分借鉴了已有工作、哪些部分确实是你们独立解决的问题。

这既可以提高后续开发的可靠性，也是在为将来的论文积累真正可解释的技术贡献。
