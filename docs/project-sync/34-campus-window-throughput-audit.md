# 旧校园三摄为什么吞吐更高

2026-10-31。用户指出旧Tartan废弃校园也是三摄，要求核查为什么现在仍慢。本轮仅查代码和旧工件，无新模型请求或服务变更。

## 关键发现与前述说法纠正

旧校园的主要建忆入口不是逐观察固定方法2，而是`src/desktop/prepare-campus-memory.ts`＋`SpatialContextLoop.runWindow`＋`spatialContextVlm`：**通常一次VLM处理连续4观察，每观察三摄，一次交付12张图，为4观察分别返回简短assessments。** 不是4次独立感知，也不是逐候选全历史分页。

历史实际完成包：`run/campus-spatial-memory/2026-10-20T13-42-03-856Z-ecad0254/`。

## 与当前的真正差别

- 原固定方法2：一次观察可能多次VLM，候选和成员分页放大。
- 新快速更新器：已降到一次/观察，但仍没有恢复一次处理多个观察的摊销收益。
- 三Agent基础版：解决隔离阻塞与恢复，不自动缩短VLM；A/B若重复逐观察理解，还会增加工作。
- 旧校园窗口：一次/4观察，约7秒完成一个通常覆盖约8秒采样预算的批次。新方案约5秒/观察，虽然单请求更快，**吞吐反而更差**。

之前“校园只是缓存回放/虚拟时钟，因此不能实时”的解释不完整：网页确有独立预建记忆和预计算结果回放，90题也采用阻塞时钟，不能拿播放观感证明实时；但旧建忆本身确实存在已运行的批处理优势，不能忽略。

## 正确的后续方向

保留三职责架构，但B首先复用现有runWindow思路：最多4个连续观察一次联合处理、为各观察保留独立时间/ID/证据；A仅按明确新鲜度需求/关注任务触发，不再对B每批原片重复全套描述；C保持原图回退与预留槽。

按最多12图预算分配：若当前批已用12图，历史原图深查应独立任务或缩小本批，不得悄悄删当前观察。迟到、来源、历史版本校验保持不变。

验收分别报告：窗口收集时间、推理延迟、观察摊销吞吐、持久待处理水位、事件/重访表现。不能再用问答8.16秒或单次5秒替代吞吐指标，也不能仅以多Agent数量称提速完成。
