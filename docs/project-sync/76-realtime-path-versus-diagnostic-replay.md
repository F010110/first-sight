# 确认：近期慢评测没有使用原实时生产路径

用户要求核查813帧是否本应30分钟内处理。此次只审计代码和既有实测，没有新增付费运行或切换服务。

## 原实时路径有实测依据

`src/assistant/three-agent-factory.ts`：parallelMemory默认true，独立提取默认2槽，eagerExtraction开启；batchMax=1时每观察一次三摄请求，最多160汉字/256输出token；`associateWindow`直接finalizeObservationFacts，不每帧再调用一次关系模型，关系按需核查。

`run/gmod-source-bound-soak-v1/report.json`原始实测：576观察，sourceDuration1221130ms，全部完成，零失败；提取峰值2；推理p50约1692ms，事实提交p50/p95约1781/3040ms；积压峰值4，尾段不增长，停止输入后约2105ms追平。有限负载下已达到用户接受的软实时。严格原验收为false，不能抹掉p95/max/交互等严格项失败；也不证明长期语义和身份关系质量。

按约2秒一观察的节奏，813观察约1626秒（27.1分钟）；以该次约2.12秒节奏估算约28.7—28.8分钟。它们是原事实生产路径的合理预期，不是新813样本已经完成的实测。旧输入速率是源节奏，不能拿它冒充无节奏满载吞吐极限。

## 最近入口不同，不是简单关掉了一个开关

`runSpatialPipeline`直接调用`createSpatialSession`，不经过createThreeAgentService的持久调度器。诊断选项diagnosticPerView=true造成每时刻三个独立视觉调用，再由Pi请求record_context/可选工具；该runner逐帧await。

`run-full-memory-standard-evaluation.ts`目前仍调用这个串行runSpatialPipeline，并且依赖已被用户否定的813细节标准。因此不能拿这个旧入口直接启动正式全量，它已不是当前推荐入口。

新写的`run-fast-spatial-replay.ts`有8帧预取+有序提交，24帧41.334秒只是小样本；它不是原实时算法，也未证明完整评测30分钟。不能用它来暗示原系统本来不够快或必需8路才可运行。

## 结论和下一步边界

用户判断基本正确：原实时事实处理有30分钟级覆盖813观察的依据；此前慢主要是评测改走了更重的串行诊断路径。正式入口应优先复用既有独立提取/有序提交/持久化调度机制，同时保留当前Pi模块及新来源隔离，不为提速偷偷退回旧语义算法。

“813观察处理≤30分钟”与“处理+所有问题+Max评分≤30分钟”不是同一结论；后者尚无实测保证，需分别统计生成、问答、评分及总墙钟时间，并让评分对已经提交的因果快照并行执行。当前不启动全量，先修正入口及核查工作量，避免又把诊断版当实时版跑。
