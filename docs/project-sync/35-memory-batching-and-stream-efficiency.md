# 记忆批处理与多维实时效率指标

2026-10-31。用户批准加入批处理，并要求以多维指标判断能否跟上，而非简单“秒/观察”。

## 实现

- B默认使用`memoryWindow`，最多4个连续观察/12张图；首观察入库后最多等待6秒开始小批，输入结束显式flush尾批。不同recording或超过2.5秒的源时间间隙提前关闭窗口。6秒是窗口形成等待上限，**不是含前序任务和推理在内的完成时限**。
- 每个观察保留独立结果和任务，单条引用/协议错误只使该条失败，不删除同批有效结果；未完成空洞保留在水位中，不能用后续结果掩盖。
- 历史原图按剩余图片预算加入；4×3图占满12图时只附历史解释，不静默漏掉某个当前观察。每个观察仍必须实际检查本观察原图。
- `results.evidence_until_ms`记录本次VLM看过的整个窗口结束时间。即使较早观察只引用自身，也不能在窗口结束前的历史快照中泄漏它的批处理解释；窗口内部直接引用未来观察仍被拒绝。
- SQLite新增接收时间与efficiency_events，兼容旧三Agent数据库，原工件不覆盖。
- `stream-efficiency.ts`汇总分布、吞吐、队列、水位、追平、当前新鲜度和交互；`run-three-agent-stream.ts`按原始相对时间回放最多32观察，后台不阻塞输入，期间实际提交一个问题并走Planner。

## 指标定义

|维度|指标|判断什么|
|---|---|---|
|采集/入库|预期与实际归档数、到达迟到、归档p50/p95/max|是否丢输入或被模型阻塞|
|窗口|批大小、首末接收跨度、收集＋前序排队耗时|批处理吞吐换来了多少等待|
|执行|请求槽等待、批推理p50/p95/max|慢在排队还是模型请求；波动大小|
|可用性延迟|每观察从源时刻到语义提交；首次语义完成|用户经历多久之后可用，含窗口收集|
|语义滞后|最新原始时间－连续完成前缀；最老未完成任务年龄|记忆落后多少，而非只看最新一次结果|
|稳定性|输入速率、输入期间提交速率、尾段未完成队列斜率、峰值队列|持续输入是否越积越多|
|恢复|输入停止后语义追平时间、所有worker排空时间|只是暂时波动还是需要长时间补课|
|当前感知|结果年龄、新鲜结果比例、过期跳过及失败|不能用历史记忆吞吐代替当前感知实时性|
|交互|问答模型通道耗时、含Planner/排队/交付端到端耗时、任务状态|用户请求是否被后台阻塞|
|完整性/质量|输入结束时完成比例、最终覆盖率、失败；语义准确率另测|最终补完不等于实时，执行成功不等于正确|

分位数为记录事件采样，不是均匀时间加权；源时钟/主机墙钟/实际推理耗时分开。首个连续结果出现之前的lag为未知，以startup和oldest unfinished指标补充，不当作零。

目前自动诊断只会给`insufficient-evidence`、`degraded-failures`、`backlog-growing`或`needs-slo-review`，**没有在未定义产品SLO时自动宣布系统通过**。至少60秒和5批才分析稳定性；一分多钟仍不足以证明全天稳定。

## 结论

**本前缀没有达到持续跟上输入。** 批处理已恢复吞吐摊销，但推理长尾和已有前序任务造成增长；A也未达到当前新鲜度要求。不能拿最终32/32或问答正常宣称整个系统实时达标。

软件验证：build通过，63项相关测试通过，含窗口等待/尾批、跨记录边界、历史未来门禁、单条失败不抹掉同批有效项、队列空洞、水位和交互多阶段计时。

后续先减少A/B重复分析、控制批输出与历史上下文、查推理长尾；同一源节奏做对照，继续分别报告采集、当前、记忆、交互与质量。更长回放和独立重访/事件准确率尚未完成。
