# 积压时的自适应并行：先拆依赖，不能只增加API槽位

2026-10-31，用户提出积压时提高并行度、真正有依赖的工作仍串行。本轮检查现有实现，未启动新模型请求、未修改线上服务或宣称该方案已实现。

## 代码确认

- `three-agent-service.ts`的workers按lane存一条Promise，B的`drainWindows`必须等待本窗口模型返回并逐观察提交后才取下一批。
- `three-agent-store.ts`的ready/claim逻辑在memory lane有running任务时拒绝第二批；仅提高AgentSlots容量没有作用。
- B目前一次VLM同时做当前窗口原图检查和历史关联，因此整个慢请求绑定最新语义context；直接并行B会产生过期context与memory_version冲突。
- 批处理和并行不是同一机制：批处理摊销一个请求处理多个观察，当前批与批之间仍串行。

## 建议保持3个逻辑Agent，B内部拆流水线

1. 并行证据提取：各窗口以原图和自身时间为输入，独立提取可见事实、动作线索、未知和证据引用。默认一个worker，积压时在预算内增到两个。不做需要最新全局身份的确定判断，不直接改地点/对象身份。
2. 提取结果立即进入持久证据层，可以乱序完成，但源时间/窗口可用截止时间保留，不能用于更早历史查询；乱序结果缓冲有界。
3. 顺序关联/提交：消费已提取证据并读取最新记忆，处理跨窗口身份、物品状态和事件因果。数据库事务短且不持锁等待VLM。正常证据写入不能每批都强制再走一轮重模型；真正不确定的关联另设待核查任务。
4. 复杂关联确需串行推理时保留依赖和质量，不强行与后续相互依赖任务并行。无关对象/片段可按依赖键分区；早期没有可靠对象/地点键时先保持候选而非伪造分区。

不增加一个长期“提取Agent”：上述为同一B角色内部的多个独立任务worker，A与按需C分工不变。A能复用已提取原图事实时不重复描述；依赖截止时间仍需明确。

## 并行度控制建议，尚未验证的参数

- 第一轮只开放1→2，不无限扩容；依据就绪窗口数、最老等待、队列趋势和实测处理速度，带滞回/冷却，不因一帧迟到频繁切换。
- C保留请求槽。B两并发＋A同时运行＋C预留需要总槽位4；若维持现有总槽位3，A非必需时才能让B占两个后台槽。不能声称不加资源就让所有角色都获得独立保证。
- 达到API限流、单次延迟随并发明显增长、错误率或预算风险上升时，不继续增加并发。相同独立工作并行不必增加总调用数，但短期请求/token速率提高，重试或重复推理会增加成本。
- 满载时先保证原始证据入库和已授权交互，尚未理解的片段持久保留；超过允许资源上限仍可能积压，不能保证任意输入下无限时间不积压。

## 质量与评测门禁

- 不用陈旧全局记忆并行作最终身份决定；关联阶段检查依赖版本。
- 窗口边界动作需要保留过渡证据，必要时使用有界重叠，但重复图不重复计作新增经历，遵守12图预算。
- 分别报告证据提取水位、身份/事件关联水位、未决核查数量，不把“提取完”改名为“完整理解完”。
- 同源节奏分别测单提取worker和双worker：队列趋势、p95滞后、追平、API长尾/限流、成本，以及重访/跨窗口事件质量。当前没有独立gold时不能只凭执行成功证明质量不下降。

此方向优先于直接把现有memory lane改成多writer。后者可能带来版本冲突、重试和错误关联，既不一定快，也不保持质量。
