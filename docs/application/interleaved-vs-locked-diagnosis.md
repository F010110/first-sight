# 冻结93分版与16轮连续版输出对照

## 基准与边界

旧版：`run/school-spatial-oracle-v1/spatial-memory-runtime-fixed-v4`原始回答，加`spatial-memory-locked-protocol-v1`已执行的锁定元数据修复；三卡93.3/94.1/97.2。修复不改回答正文，不能理解为新的独立90题。新版：`run/interleaved-memory-90-budget16-v4`，47.8/26.5/98.3。

两侧不是严格控制变量：旧版建库后按因果范围独立问答；新版连续建库、持久短期Context、窗口空间判断与问答共用输出；问题由录像相对地址换为假设日期ISO地址。因此不将全部分差归因于某个因素。

## 离线逐题证据

`sim/compare_interleaved_outputs.py`读取全部90题新旧结果及新版原始provider回执，按问题正文+当前观察ID匹配（正文可能重复，不能只按正文匹配）。完整对照：`run/interleaved-vs-locked-output-comparison-v2.json`。不调用模型，不改原答案。

- 新版44题没有最终答案。
- 44/44题的全部已解析模型动作都是search。
- 44/44题在调用输入中已出现公开问题要求的历史原图候选ID。
- 44/44题没有任何inspect动作。

这证明共同失败位置是**候选已检索到→模型选择inspect**，而不是这些题的目标图片根本未入库或检索不到。不能据此证明其他任务的空间图正确，也不能断言修复后必得原分数。

## 代码层差异与解释强度

1. **提示没有随取证状态推进。** `src/agent/spatial-context-vlm.ts`末尾只按requiredIds是否已inspect区分状态。缺图时，无论候选是否已找到，都会再次强调“用完整ISO作为search.query，再inspect”。另一个clock提示也反复要求search。它没有明确分开“未找到→search”和“已找到未看图→inspect”。这是代码事实；其因果贡献还需捕获输入对照探针验证。
2. **无进展检测/反馈。** `spatial-context-loop.ts`执行search后只替换candidates，不记录专门的成功工具反馈，也不提示“相同查询已返回以下ID，请inspect”。重复相同search合法，16轮均可消耗在同一操作。这与44条原始调用链一致。
3. **交互表达不同。** 新版每次将Context、旧输出、候选和当前问题一起序列化为单条user多模态消息；旧问答路径使用专门的工具协议及final-ready约束。新版旧动作会作为未核实outputs再次进入输入，存在动作模仿/问题干扰风险；已有冒烟出现复制前题拒答，但不能仅凭此给44条循环全部作因果归因。
4. **连续空间任务增加负担。** 新版每一轮还必须重写最多4条空间判断，旧问答记录通常仅1个当前观察。属于混杂因素；目前最直接可见故障仍是search→inspect没有推进。

## 下一步（尚未实施/尚无新分数）

- 按真实工具状态明确分三段：缺候选才search；有候选未看图就inspect；原图已到则回答或明确拒答。候选仍不能当已看图。
- 对重复查询返回明确的已执行工具结果和无新增候选提示；保留原动作，不静默改写为inspect，不靠私有正确答案选图。
- 区分当前活跃问题、已结束问题与旧模型输出，保留双写，不让旧输出成为待执行命令。
- 先用保存的失败输入和成功输入做小规模对照探针，控制图片、模型、Context及轮数；验证实际出现inspect、图像交付与正确最终引用。不要直接再盲跑90题。
- 再运行新的独立90题，旧版和失败版不覆盖、不拼接。

本诊断没有修改算法或启动付费重跑。此前把症状优先解释为预算过小并不充分；4→16轮对照已经否定“只加轮数就能修复”的预期。
