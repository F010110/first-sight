
我认为现在可以提出几条真正不同于你原来三种方案的路线了。

你原来的选择是：

1. 让每次空间判断更快。
2. 修改并发架构，容忍更长的判断时间。
3. 把8秒一次判断改成10–12秒一次。

这三种方法有一个共同前提：每个时间窗口都应该由空间 Agent 完成一次完整判断。

但我重新看了 StreamMind、EventMemAgent，以及此前没有重点讨论的 ORB-SLAM3 后，觉得这个前提本身值得改变。

我现在最推荐的方向是：保留高频观察，但让昂贵的空间推理按需发生，而不是按固定时间窗口发生。

这不是单纯降低采样率。它意味着把“观察”“状态跟踪”“复杂身份判断”和“长期记忆整理”四种工作从执行频率上解耦。

## 一、研究中真正值得借鉴的四种新机制

| 机制                      | 相关研究                             | 新在哪里                                       | 我对 First-Sight 的判断      |
| ------------------------- | ------------------------------------ | ---------------------------------------------- | ---------------------------- |
| 事件驱动的空间判断        | EventMemAgent、ORB-SLAM3             | 不再每个窗口都运行完整推理                     | 最推荐                       |
| 快速状态跟踪 + 慢速重定位 | ORB-SLAM3                            | 大部分连续时刻沿用已有状态，只在必要时重新识别 | 非常值得测试                 |
| 推测性判断 + 有序确认     | 流处理/并发控制思想                  | 后续窗口提前计算，但不能无条件提交             | 值得研究，风险较高           |
| 渐进式记忆更新            | StreamMind、SLAM 的局部建图/后台优化 | 先形成可用状态，再延迟完成复杂整理             | 有价值，但要避免破坏事务语义 |

其中前两种可以结合，甚至可能让你们不必在固定8秒预算内完成一次完整的 Pi 推理。

### 方案 A：事件驱动，而不是固定窗口驱动

EventMemAgent 不再单纯按照固定帧数保留历史，而是检测事件边界，以事件为单位构建短长期记忆。它本身不是空间身份识别系统，但其事件组织方式可以作为参考。

[image](https://www.google.com/s2/favicons?domain=https://arxiv.org\&sz=32)

arXiv

First-Sight 可以借鉴这种思想：

- 用户在同一个房间内稳定移动，没有新的空间信息：不必重复执行完整身份判断。
- 用户经过门、楼梯、走廊交叉口：触发空间边界判断。
- 当前视觉与已知地点发生明显冲突：触发身份核验。
- 很久没有完整判断：设置最大间隔，强制执行一次以避免长期漏检。

最关键的是：仍然每2秒接收、理解和归档观察，只降低昂贵的空间身份判断频率。

你们现在的 Perception 已经单独运行，因此特别适合考虑这种调度。

但事件检测不能依赖先完成 Pi 判断，否则就会循环依赖。事件触发器必须能够从 Perception facts、轻量视觉特征、已有状态及时间信息中运行。

### 方案 B：快速状态跟踪 + 慢速重定位

这是我认为比前三篇视频 Agent 论文更重要的参考。

ORB-SLAM3 将实时跟踪、局部建图、回环检测与全局优化分成不同执行模块。它在正常跟踪时并不要求每帧重新运行完整的全局地点识别；更昂贵的建图和回环校正可以在其他执行链路中完成。

这里要小心：ORB-SLAM3 的快速跟踪依赖几何特征及其自身地图表示，不能直接用于你们没有精确坐标的语义空间系统。

我的建议是借鉴它的分级计算原则，不是移植整套 SLAM。

如果同一房间内连续5个窗口都没有明显变化，你们不一定需要5次完整的 Pi 判断。

但若某个窗口处于新区域、回环或歧义状态，就必须触发更完整的证据核验。

这是一种计算资源分配方法，而不只是固定降低调用频率。

### 方案 C：推测性执行，但不允许乱序改变已确认状态

这是对你们原来「增加并发窗口」方案的一种改造。

假设 A 窗口正在进行空间判断，B 窗口已经完成 Perception。

B 不一定要等 A 完成才开始所有处理。可以提前生成基于当前已确认状态的候选判断：

窗口 A

Pi 空间判断进行中

窗口 B

按状态版本 V 预计算

A 提交后检查 B 的依赖

B 的候选是否依赖 A 改变的地点、访问或边界状态？

依赖未失效

验证后采用预计算结果

依赖失效

重新判断或降级为待判证据

这样能够容忍较长模型延迟，又不要求空间状态无条件乱序提交。

但要强调，这只是我基于并发控制思想提出的候选架构，不是上述视频 Agent 论文已经验证的现成方案。

而且它有两个风险：模型并发可能增加单次请求延迟；重新计算也可能抵消收益。

因此它更适合先做一个只读实验：让后续窗口提前运行候选判断，观察有多少结果能在前序提交后保持有效，而不真正修改主数据库。

### 方案 D：按重要性延迟处理，而不是直接跳过整个窗口

这是从 StreamMind 的异步记忆写入，以及 SLAM 的局部实时处理、后台优化中抽象出来的另一种策略。

[image](https://www.google.com/s2/favicons?domain=https://arxiv.org\&sz=32)

arXiv+1

你们现在忙时会跳过整个空间判断窗口，保存证据，再由后续窗口补判。

可以尝试改变为：

- 每个窗口仍然保存完整原始观察和 Perception facts。
- 对连续且低歧义的窗口，记录「尚未确认的连续状态」，暂不生成完整空间归属。
- 对触发空间变化的窗口，优先执行完整 Pi 判断。
- 对历史中未完成的窗口，在系统空闲或遇到回访时，以已有证据进行批量补充判断。

这与当前 `skipped_windows` 最大的区别，是把未判断窗口变成一个具有状态和优先级的待处理任务，而不是只等待后继 Agent 顺带消费。

但这种设计不能偷偷把未确认位置当成已确认事实。你们现有的 `known/new/unknown+boundary`、原始证据不可变和追加式 `revisions` 等约束都应该保留。

spatial-memory-design-and-references.md

它解决的是实时记忆覆盖的策略，不会凭空增加计算能力。如果系统长期输入的信息量超过处理能力，最终仍然需要稀疏化、聚合或降低处理频率。

## 二、还有两项新的相关研究值得补充

在这次检索中，我又找到了两项特别贴近「高频观察、低频昂贵推理」的工作。

SVMemAgent（2026）：研究在不知道未来帧、也不知道用户未来会问什么的情况下，如何在线选择和保留具有价值的视觉帧。它通过学习决定新帧应替换哪些记忆帧。

[image](https://www.google.com/s2/favicons?domain=https://arxiv.org\&sz=32)

arXiv

对 First-Sight 的启发是：空间判断的触发可以被看作一个有预算的在线选择问题。但你们应优先采用无需训练的变化检测规则验证可行性，而不是一开始就训练新策略。

Event-Driven Refresh and Recurrence Memory（2026）：在视频物体分割任务中，不再固定频率重新运行昂贵的多模态模型，而是在目标出现、消失及场景变化时触发重新确认，并利用历史视觉记忆支持目标再次出现后的识别。

[image](https://www.google.com/s2/favicons?domain=https://huggingface.co\&sz=32)

Hugging Face

虽然这是视频分割而不是空间记忆，但它与你们的实际问题非常相似：让一个昂贵但准确的模型负责重新确认，让便宜的机制负责监视何时需要重新确认。

这比单纯研究工具调用并发更有针对性。

## 三、哪种方案最值得先试？

我会按以下顺序尝试：

| 排序 | 方案                     | 对串行耗时的作用         | 风险   |
| ---- | ------------------------ | ------------------------ | ------ |
| 1    | 事件触发 + 快速状态跟踪  | 减少完整 Pi 判断数量     | 中     |
| 2    | 待判窗口优先级与延迟补判 | 降低繁忙时关键事件丢失   | 中     |
| 3    | 推测性判断 + 版本验证    | 允许部分串行工作提前执行 | 高     |
| 4    | 继续优化单次工具调用     | 缩短单个判断时间         | 低到中 |

我的选择是 先验证第一项。

因为你们已经有813帧的完整数据和现有基线，不必立即破坏主架构。

可以在同一条轨迹上做一个反事实回放实验：

1. 用现有 Perception facts、图像相似度和时间信息，生成「是否需要完整判断」的触发决策。
2. 与原来每8秒一次的固定窗口策略比较，统计新策略会触发多少次 Pi 判断。
3. 特别检查真实房间切换、重复访问、边界不明确等重要时刻有没有被错过。
4. 如果能够在不明显漏掉关键事件的情况下减少30%甚至更多的完整判断，再进行真正的在线集成。

这里的30%只是一个可以设置的探索性目标，不是论文已经保证的收益。

还有一个必要的控制：不能用完整轨迹的未来信息决定当前是否触发判断。 否则离线实验会高估在线效果。

## 我的结论

我现在认为，你们可以停止把「每8秒完成一次完整空间判断」当作不可改变的系统要求。

应该保留的是：

- 连续观测的接收；
- 原始信息与来源的完整归档；
- 空间状态的因果一致性；
- 重要空间变化及时被识别；
- 所有未确认信息都不能被当作已确认事实。

不一定要保留的是：每个固定时间窗口都必须调用一次完整 Pi Agent。

这也不等于建议马上推翻你们现有的8秒窗口和数据库设计。窗口仍可以作为证据归档单位，只是判断任务不再和窗口严格一一对应。

如果我是你，我下一步就会研究一个「事件驱动空间判断调度器」的最小实验，而不是继续在原有架构上反复处理超时。

这条路受到 EventMemAgent、在线关键帧选择和 SLAM 分级处理思想的共同启发，但还需要在 First-Sight 的真实813帧轨迹上证明它确实有效。

而且它有一个比单纯性能优化更有意义的潜在结果：你们可能最终发现，空间记忆并不需要以固定频率更新，而应该按照空间状态变化和不确定性动态分配推理计算。那时，新的 Harness 设计就不只是为了解决工程超时，而是可能成为一个独立、可验证的方法。
