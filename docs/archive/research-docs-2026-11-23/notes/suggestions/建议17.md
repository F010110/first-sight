# First-Sight v3：分层实时视觉记忆系统架构设计

我建议以你提出的 4–8秒快速分析 + 40秒完整空间分析 为基础，重新组织 First-Sight 的执行架构。

这次调整的核心不是简单降低空间推理频率，而是改变系统的工作方式：

从「持续进行完整空间推理的 Agent」，转向「持续观察、低频巩固记忆、按需响应用户的视觉助手」。

我认为它更符合你们当前的产品目标，也有望显著降低费用和工程复杂度。

不过，有三个约束必须从设计阶段就明确：

1. 40秒是记忆处理周期，不是地点划分的最小时间单位。 一段40秒的观察可能经过多个地点，不能强行归为一个地点。
2. 用户问答不等待后台空间分析。 需要时可以独立执行临时空间判断，但不能破坏后台长期记忆的一致性。
3. 快速分析不承担完整空间推理。 它只需要产生有时间和来源依据的视觉事实，不应变成另一个不断调用工具的复杂 Agent。

## 一、总体架构

持续视觉采集

三摄图像 · 时间戳 · 可选 IMU / 位姿

快速感知层 · 每4–8秒

场景、设施、物体、显著变化、视觉证据

Observation Store · 实时归档

原始图像 · Perception Facts · 时间索引 · 特征索引

后台空间分析

## 40s

地点、重访、关系、修订

长期记忆库

地点 · 访问 · 状态版本

用户交互 Agent

## 按需

即时问答 · 定向检索 · 临时空间判断

记忆查询接口

只读已提交状态及历史证据

未来扩展：环境变化记忆 Agent

基于同地点历史观察，维护物体与状态变化

这里有一个我坚持的设计：快速感知、长期空间维护和用户交互是三个独立的执行通道，但共享同一套观察证据和已提交记忆。

你们此前将图像理解与空间推断拆开的工作可以直接保留，不需要推倒重来。

## 二、三条执行通道分别做什么？

|                          | 快速感知     | 后台空间分析                 | 用户问答                 |
| ------------------------ | ------------ | ---------------------------- | ------------------------ |
| 触发                     | 每4–8秒     | 约40秒                       | 用户主动请求             |
| 主要输入                 | 最近三摄图像 | 近期事实、必要原图、历史地点 | 问题、最近观察、长期记忆 |
| 模型任务                 | 提取事实     | 判断地点、重访、更新空间结构 | 解答具体问题             |
| 长期工具调用             | 不需要       | 允许                         | 按需、只读为主           |
| 是否必须串行             | 否           | 是                           | 不与后台串行队列绑定     |
| 是否直接修改长期空间状态 | 否           | 是                           | 默认否                   |
| 是否允许延迟             | 有界         | 允许一定积压                 | 优先低延迟               |

### 快速感知：不再承担空间身份判断

每4–8秒处理最近观察，输出结构化事实。例如：

```
{
  "timeMs": 120000,
  "observations": [
    {
      "sourceId": "frame_060",
      "summary": "室内走廊，左侧有楼梯入口",
      "details": [
        "前方是长走廊",
        "左侧可见向上的楼梯",
        "右侧有关闭的门"
      ]
    }
  ]
}
```

它不需要判断「这是之前的楼梯间吗」，也不负责创建地点。

我建议快速感知尽可能采用无历史、无工具循环的模型请求，以减少 Context 成本和长尾延迟。

但它不应该只输出每批图片的整体摘要。你们之前的 Perception 已经实现了按观察 ID 绑定事实，这个设计应该保留。

尤其是场景过渡期间，即使只有一帧出现楼梯，后续也应能够准确检索到这条事实。

### 后台空间分析：从40秒证据块中恢复地点变化

这里有一个很重要的技术区别。

我不建议将40秒图像全部拼成一个大型 Prompt，然后让 Pi 判断它们是否属于同一地点。

更合理的是利用快速感知产生的时间序列，优先推断其中的地点连续性与变化，并在必要时读取原图。

这是一个关键的架构目标，而不是已被证明一定可靠的能力。需要测试模型能否根据时间序列稳定地输出多个空间片段；如果不能，就必须允许不确定边界或局部补判，不能强行完成归属。

这里我建议保留原先8秒观察窗口作为可引用的证据单位，但不再要求每个窗口完成一次独立 Pi 判断。

## 三、用户提问：独立快速通道 + 按需补充推理

这是整套新架构最重要的部分。

我建议不要让用户问答 Agent 每次都执行完整的空间分析，而是根据问题类型选择不同的处理路径。

用户提问

Query Router

判断问题需要哪些证据和能力

当前视觉

直接读取最近观察

历史回忆

检索已提交长期记忆

当前定位

按需视觉重访匹配

复杂空间推理

定向补充、必要时升级分析

Answer Agent

整合证据、生成答案、报告不确定性

具体可以按以下方式处理：

| 用户问题                       | 推荐执行路径                                    |
| ------------------------------ | ----------------------------------------------- |
| 「前面是什么？」               | 最近视觉事实，不等待长期记忆                    |
| 「刚刚经过了什么？」           | 近一分钟观察时间线                              |
| 「之前在哪里见过电梯？」       | 长期记忆检索、证据核实                          |
| 「我现在在哪里？」             | 快速地点候选；不足时触发定向重访                |
| 「我是不是回到了刚才的站台？」 | 当前图像与历史候选比较                          |
| 「从这里怎么回大厅？」         | 当前位置判断 + 长期空间关系；信息不足时明确说明 |

这里我建议设置一个按需空间推理器，但暂时不把它设计成另一个完整的持续 Agent。

它可以借用现有的重访候选、图像检查和地点判断能力，以只读快照运行。

例如：

用户询问「我现在是不是回到了刚才的站台？」

系统不必把尚未处理的40秒观察全部写入空间记忆库，只需要获取当前几张图与候选站台的历史图像，让模型判断是否存在足够的同地点证据。

如果判断可信，可以先回答用户，但结果只作为临时判断保存。是否正式改变地点身份，由后台空间记忆流程处理。

这样就避免了两个 Agent 同时修改长期空间状态。

### 用户问答需要抢占后台吗？

我的建议是：优先级高于后台，但不强制中断正在进行的空间分析。

用户问答可以使用独立的模型请求和只读数据库连接。

当模型服务或并发额度紧张时，暂停启动下一轮后台分析，优先保障用户请求；已经开始的空间判断可以正常完成。

这比强制取消 Pi Session、回滚工具执行和重新恢复状态简单得多。

同时，还需要提供回答超时后的降级策略：有最近观察就先回答能确认的部分，不能因为历史重访判断耗时过长而无限等待。

## 四、长期记忆应该怎样保持一致？

这次我不建议重做你们已经建立的 SQLite Schema v4、事务提交和追加式修订机制。

但需要新增一个概念：记忆处理进度（Watermark）。

例如：

系统当前时间

12:05:00

已归档观察

12:04:56

已完成快速分析

12:04:48

已提交空间记忆

12:04:20

示意时间与进度，不是实际运行状态。

用户问答应当能够读取三个不同的新鲜度：

- 最新已归档的图像。
- 最新已完成的感知事实。
- 最新已经提交的空间记忆。

这样即使空间记忆落后40秒，用户仍然可以利用最近几秒的观测回答当前视觉问题。

另外，长期记忆应当记录已经连续处理到什么时间点，而不只是最近一次提交的时间戳。否则一次跨越旧数据的异步修订，也可能被误当成当前进度已经推进。

这与现有不可变快照、来源引用和事务机制兼容。

## 五、40秒空间分析发生超时怎么办？

这里我建议改变你们原来比较激进的「忙时跳过」机制。

以前每8秒有一个空间判断任务，单个任务超时很容易导致后续窗口被跳过。

现在40秒一次，空间 Agent 应当拥有更宽裕的运行时间。

但不能简单地允许它无限执行。

我建议采用下列规则：

| 情况                   | 系统行为                                     |
| ---------------------- | -------------------------------------------- |
| 40秒内完成             | 正常提交                                     |
| 超过40秒但仍在执行     | 后续观测继续采集，后台任务不并发修改空间状态 |
| 下一批观察已经就绪     | 放入有界待处理队列                           |
| 长期处理速度跟不上输入 | 合并尚未分析的相邻证据范围，或标记待补判     |
| 某批反复失败           | 保留证据并记录失败，不让整个后台停滞         |

最重要的是，不应因为空间判断缓慢，阻塞快速感知和用户问答。

而且合并证据范围不等于合并地点。如果80秒的观察需要在一次调用中处理，模型仍应允许输出多个地点片段及不确定边界。

对于持续超载，还应该明确暴露 backlog 的时间跨度，让用户和开发者知道长期空间记忆究竟落后了多少，而不是只显示系统仍在运行。

## 六、对重访 Agent，我建议作出一个架构调整

你们最近已经准备把重访判断从主 Pi Agent 中拆出来。

我支持功能解耦，但不建议同时维护两个不断增长的长期推理 Session。

更合理的设计是将重访作为一个可复用的判断服务：

Place Matching Service

它接收当前观察和候选历史地点，返回：

```
{
  "candidatePlaceId": "place_17",
  "decision": "same",
  "confidence": "high",
  "evidenceIds": ["frame_040", "frame_205"],
  "reason": "可见布局和关键设施高度一致"
}
```

它不直接创建地点、不修改访问历史、不提交新的空间状态。

后台 Pi Agent 可以调用这个服务；用户问答也可以调用它。

这样同一套重访能力不会重复开发两遍。

但有一点需要保留：Place Matching Service 应当支持 `same`、`different`、`uncertain`，并且高置信判断也要有来源依据。上面的 `confidence` 只是候选协议字段，不代表模型输出的置信度已经经过校准。

## 七、环境变化 Agent 将来怎么接入？

这次架构最好提前为环境变化预留位置，但不立即实现。

我建议它采用地点关联的独立记忆维护流程：

历史观察

同地点旧证据

最新观察

本次访问事实

环境变化分析

物体身份、状态差异、出现/消失、变化证据

变化记忆库

地点关联 · 物体状态版本 · 时间与来源

这里仍然应当允许空间位置不确定时先保存观察，等位置得到确认后再做跨时间关联。

因此未来的环境变化 Agent 不需要和空间 Agent 在同一个串行通道运行。

## 八、建议的运行参数与验收要求

下面这组参数可以作为 v3 的初始配置，而不是最终产品标准。

| 配置             | 建议初始值                     |
| ---------------- | ------------------------------ |
| 三摄采集         | 保留现有节拍                   |
| 快速 Perception  | 6秒一次，允许4–8秒调整        |
| 空间分析         | 每40秒生成一批待分析证据       |
| 后台并行空间写入 | 1条串行通道                    |
| 重访判断         | 按需调用，不持续轮询           |
| 用户问答         | 独立高优先级通道               |
| 用户即时回答目标 | 先测试数秒内返回有依据的答复   |
| 完整空间判断     | 可超过40秒，但必须监控持续积压 |
| 长期存储         | 沿用事务、版本与来源体系       |

这里必须注意：你们原来 Perception 的粒度是一个8秒窗口包含最多4次观察。新周期如果调整为6秒，应该修改的是触发调度，不要不经测试就改变事实来源绑定规则。

### 我建议重点测量五项指标

- 快速感知的 P50/P90 延迟以及漏掉的关键视觉事实。
- 空间记忆落后于真实观察的时间。
- 40秒批处理中地点误合并、误拆分及重访正确性。
- 用户问答的端到端延迟、正确率和超时率。
- 每30分钟的模型成本，以及各通道的成本占比。

特别是用户问答，不应该只测试后台空闲时的响应速度，还要测试后台正在执行复杂重访、压缩和空间提交时的响应。

## 九、如何从现有系统迁移？

我不建议再来一次全面重构。

最稳妥的办法是在现有架构上分阶段调整。首先保留数据库、证据机制、Pi Skill、已建立的恢复和审计能力，只修改调度方式。

第一步，将现在「观察窗口 → 立即空间判断」的绑定关系解开。快速 Perception 按自己的节拍运行，40秒积累的观察再进入 Pi 的空间分析任务。

第二步，让空间分析能够对一个40秒批次输出多个地点片段，不再默认一个判断对应一个地点。这一步必须先用813帧样本验证，不能直接假设模型能够做到。

第三步，将重访能力整理成独立、只读、可复用的 Place Matching Service，由空间 Agent 和未来问答 Agent 共用。

第四步，接入用户问答的只读查询通道，并建立必要时的临时空间判断能力。

最后再实现环境变化记忆，不要同时改动所有部分。

## 最终建议

我认为这套架构有一个值得坚持的原则：

观察应当连续，空间记忆可以延迟，用户交互必须按需及时响应。

目前你们最大的架构问题，可能就是把这三者绑定到了同一个空间判断循环中。

新系统并不一定需要更强的模型，却能更合理地分配推理成本。不过40秒一次的空间分析是否足够准确，仍然需要实验验证，尤其是这条连续移动的813帧样本。

我建议给 v3 设置一个明确的工程目标：

在30分钟连续移动测试中，以显著低于当前约5元的成本，保持可查询的主要地点与回访记忆；同时在后台空间分析运行期间，仍能及时回答用户关于当前环境和历史地点的问题。

如果实现了这一点，First-Sight 就不仅仅是一个能够持续建图的空间 Agent，而是开始成为一个真正可交互、可长期运行的视觉记忆助手
