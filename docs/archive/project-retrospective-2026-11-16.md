## 1. 结论摘要

### 1.1 一句话概括这一个多月

项目从一个“拍照—场景描述—用户提问”的多Agent原型，逐步发展成带真实相机接入、原图归档、SQLite长期记忆、持续空间Session、独立问答、来源与因果校验、实时调度和可恢复实验的研究型系统；**工程闭环有实质进展，但可靠的地点身份、重访和长期自主检索仍没有得到充分验证。**

暂停并不是因为没有做出东西，也不能简单归结为机器算力不够。主要矛盾已经由“接口接不通、数据拿不到”转向：

- 系统到底知道观察者站在哪里，而不只是看见了什么？
- 两段相似画面是否真是同一个地点，还是相同装修、同类店铺、共享背景或街口的不同侧面？
- 存下来的历史能否在真实问题出现时被主动、准确、及时地找回？
- 面对持续输入，如何同时保持新鲜度、完整性、因果性与有界计算？
- 怎样用可信的评测回答这些问题，而不是被自动高分、固定ID命中率或小样本演示误导？

### 1.2 可以保留的主要成果

1. **多代可追溯原型。** Git从2026-10-03开始，共301次可达提交；保留V1、V1.1各研究版、V1.2、V2、V2.1标签，没有用最后一版覆盖整个研发历史。
2. **真实相机和桌面闭环。** ESP32-S3单摄采集、串口与Wi-Fi传输、主动上传、预览、记录、回放、只读历史问答实际接通过；三摄设备身份、方向和网页预览也有短测证据。
3. **持续记忆底座。** 原始观察、独立事实、地点、访问、来源、追加修订、版本快照、SQLite事务、Pi Session、压缩与检查点逐步建立，不只是把最近几条描述拼到prompt里。
4. **完整运行证据。** 早期851观察/90题问答运行和后期813组三摄空间运行均有真实完成记录。2026-11-09的40秒批次基线实现813全归档/空间覆盖、0跳过、0投递违规，耗时约27分22秒。
5. **可控的数据与审核设施。** UnionCity最终813组三摄、42段参考、双时钟、原图hash、操作重放、电梯修复、逐帧网页审核等资产可继续复用。
6. **独立视觉模块的计算优化。** 最终813查询的ULVN相关重访实验在RTX4060 Laptop上完成，端到端8分31秒，41个窗口全部低于40秒；无需先升级4090或上云就能完成这个独立模块的计算预算。
7. **有价值的负结果。** 多种提示词、检索、分组和视觉认证方案均留下具体失败与可核查证据；尤其明确了“图像对应成立”与“同一占据地点成立”的区别。

### 1.3 暂停时不能声称完成的事情

- 不能声称实现了可靠的全天、多日、跨环境生活记忆。
- 不能声称空间身份和重访已达到可靠产品标准。
- 不能把旧90题高分当成后期UnionCity重访准确率或真实用户成功率。
- 不能把813计算完成、输入实时或单元测试通过当成空间语义通过。
- 不能声称三台硬件摄像头已经实现同步、标定、持久三视图录制和长时稳定模型输入。
- 不能声称已实现完整GPS/地图融合、真实IMU主链、室内精细定位或安全导航。
- 不能声称最后的完整VLM＋ULVN系统已跑完813；该轮在约70分钟时由用户要求中止。
- 不能声称当前全部工作已经进入Git或远端；11月11日大量关键实现、报告和评分仍是本地工作区内容。

### 1.4 暂停决定的技术含义

本阶段更合理的结论是：**纯靠当前VLM身份判断或局部视觉几何匹配，承担全局地点身份认证，风险已经有实际证据；继续简单换prompt、换matcher或调阈值，没有足够理由保证能够收敛。**

较准确外部定位＋已有地图是值得未来优先评估的方向，尤其适用于室外；室内则需要建筑/入口锚定后的局部连续建模、楼层及重访判断。它是讨论中的方向，**未完成新架构批准、实现或实测**。本次暂停后不自动开启相关实验。

## 3. 项目到底是什么：目标、系统架构与工作原理

本章先解释系统本身，不要求读者先看代码或Git。以下以后期明确的职责为主，同时区分目标与实际实现；不是说V1从一开始就包含了所有模块。

### 3.1 服务对象、核心问题与产品边界

First Sight面向盲及低视力用户，希望把持续第一视角观察变成可查询、有来源的生活记忆，用自然语言帮助理解当前环境、回忆此前经历、寻找最后见过的物品和解释走过的路线。

| 用户问题                         | 系统必须真正具备的能力                       | 只有图片描述为什么不够                                   |
| -------------------------------- | -------------------------------------------- | -------------------------------------------------------- |
| “现在这里是什么地方？”         | 当前观察、实际占据区域与身份判断             | 看见远处商店，不代表站在商店里                           |
| “我刚才是不是来过？”           | 连续性、历史重访、旧地点身份和独立访问       | 两段画面都叫走廊，不代表同一走廊                         |
| “最开始那家店的桌子是什么样？” | 时间/场所指代、历史定位、取回对应原图        | 当前洗衣店的桌面再清楚，也不是所问历史                   |
| “钥匙最后在哪里看见？”         | 物品实例、可追溯最后所见、采集空白与未知状态 | 存过大量图片，不等于知道哪个是同一把钥匙或它现在还在原处 |

项目还探索过目标关注、读文字和路线说明，但没有完成这些能力的统一真实用户验收。**它不是机器人控制器或安全避障器；“经过过”不能自动变成“现在能安全走过去”。**

### 3.2 实际部署：硬件、接收、后端和前端

真实相机原型与后期离线研究链路分开存在，共享部分软件，但不是全部已经合并。

```text
真实相机原型
ESP32-S3 / OV2640
  │ JPEG、设备ID、方向、序号与时间相关元数据
  │ 早期串口，后改校园Wi-Fi / HTTP主动上传
  ▼
Python接收进程
  ├─ 校验鉴权、长度、hash、尺寸及序号
  ├─ RAM最新帧 → 预览
  └─ 记录开启 → 原图和记录日志
  ▼
Node.js / TypeScript服务
  ├─ 相机会话、记录控制、生命周期
  ├─ 空间生产、SQLite记忆与模型provider
  ├─ 问题Agent、来源校验、用量预算
  └─ 本机HTTP接口
  ▼
浏览器：预览、系统/记录开关、问题与回答、历史回放

离线研究
公开观察清单 + 三摄文件
  → hash/方向/时序校验 → 按显式时钟投递
  → 同类记忆运行器 → 空间库/Session/请求/收据

独立评测侧
冻结结果 + 私有参考/地图 → 评分与视觉审核
```

固件不运行VLM；浏览器不持有模型密钥，也不执行空间数据库事务。默认预览、单独记录、启动付费分析是不同状态，不能把网页有图当成模型已分析。回放读取已有图和结果，不等于重新调用模型。

离线三摄是同一源时刻的多个方向，不意味着真实三台硬件已完成曝光同步、外参标定和稳定三路模型输入。地图和位置参考只在评测侧；不能将它们送给生产后再报视觉准确率。

**主要技术组成及其作用：**

| 技术/运行设施                      | 具体承担什么                                                      | 不应误解为什么                                          |
| ---------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------- |
| TypeScript / Node.js               | 主应用、Agent工具、调度、HTTP服务、SQLite访问与评测运行器         | 不是所有能力都在一个主函数里；不同入口仍有迁移差异      |
| Python                             | 相机接收、数据制作、图像特征/匹配、部分只读分析与评分             | 图像子进程和模型API不是同一个成本；IPC也会产生开销      |
| SQLite及图像文件                   | 业务记忆、来源/修订/快照、原始证据                                | 不需要额外远程数据库，但仍有WAL备份、容量和故障问题     |
| Qwen视觉语言API                    | 多数阶段的感知、空间解释、问答；后期以qwen3.8-flash为主要被测模型 | 不是本地运行一个通用小VLM；云请求受网络、配额和费用影响 |
| Qwen Max/Flash评审                 | 不同阶段的开发裁判与有界复核                                      | 换裁判不代表被测算法升级，同模型族也不等于独立人工      |
| Pi Agent Harness / Session / Skill | 角色规则、工具循环、可见轨迹、Context压缩和恢复设施               | 不是自动完成地点建图/实例认证的黑箱算法                 |
| 本地视觉模型与OpenCV               | MegaLoc、SuperPoint、LightGlue及RANSAC等候选/对应计算             | 本地GPU匹配不是生成式VLM，也不是完整SLAM或GPS定位       |
| 网页、视频与浏览器语音             | 操作、呈现、回放和原型语音交互                                    | 不是经过真实视障用户验收的无屏幕交互闭环                |

核心实现是“云端语义推理＋本地业务执行/证据存储＋本地图像处理”的组合；后期增加了GPU视觉模块，但没有因此获得已验证的全离线生活助手。

### 3.3 逻辑架构：持续空间生产与独立问题服务

```text
连续观察（三摄、方向、时间）
       │
       ▼
[1] 耐久原图/元数据归档 ────────────────────┐
       │                                 │
       ▼                                 │ 最新原图只读
[2] 无历史快速感知                         │
    逐观察事实、布局、文字和限制             │
       │                                 │
       ▼                                 │
[3] 单个持续空间Agent（Pi Session）          │
    ├─ 当前区域、连续性、历史重访            │
    ├─ 主动检索与按需原图取证               │
    └─ 地点/访问维护、过渡、未决与修订        │
       ↕                    ↕            │
[4] 短期工作Context     [5] 长期SQLite+原图  │
       │                                 │
       ▼                                 │
[6] 校验 → 事务提交 → 检查点 → 发布版本      │
       └──────────────┬──────────────────┘
                      ▼
              [7] 独立用户问题Agent
              固定版本/截止，只读空间
              检索 → 读事实 → 看原图 → 回答
                      ↕
                私有问答会话、独立压缩
```

| 模块           | 输入                                    | 输出与职责                               | 明确不能做的事                           |
| -------------- | --------------------------------------- | ---------------------------------------- | ---------------------------------------- |
| 归档层         | 真实收到的图像和元数据                  | 保存原件与可追溯来源                     | 把丢帧补造成观察，记录成功当理解成功     |
| 独立感知       | 当前原图，不读历史身份                  | 当前可见事实和限制，逐观察绑定           | 为了符合旧地点猜测改写当前所见           |
| 候选召回       | 当前特征、因果历史索引                  | 若干可能相关地点/来源                    | 相似度直接当身份；空结果证明从未到访     |
| 空间Agent      | 事实、工作Context、候选、实际取回的证据 | 位置、连续性、历史关联、档案、访问、未决 | 只在用户问时临时建空间；默认沿用过期位置 |
| 短期Context    | 同一会话实际观察、工具、结论和失败      | 有界工作视图、压缩和恢复线索             | 代替全部长期库；摘要升级为新事实         |
| 长期存储与校验 | Agent提议和真实来源                     | 持久ID、事务、追加版本及查询             | 程序猜测替模型补正确身份，覆盖旧原件     |
| 问题Agent      | 本题、只读快照、最新视觉与私有历史      | 调查、回答、来源或不足                   | 把问题、答案、猜测写成空间观察           |
| 评测侧         | 冻结输入/输出、私有参考                 | 完整性、语义、失败与费用审查             | 真值补进生产记忆后报告系统正确           |

Pi是Agent执行和会话设施，不是空间数据库；SQLite保证持久化和事务，不保证被写入的语义正确；Skill规定角色和工具行为，不是一个已经证明正确的视觉算法。

### 3.4 数据模型：原图、地点、访问和窗口是什么关系

| 对象                | 含义                               | 例子与约束                                       |
| ------------------- | ---------------------------------- | ------------------------------------------------ |
| 观察 Observation    | 某个发生时刻的原图、方向和来源     | 三摄是同一时刻不同朝向，不是三个时刻             |
| 独立事实            | 对观察的模型感知结果               | “可见绿色桌面”不是人工真值，也不证明地点身份   |
| 空间判断 Assessment | 当时证据下对位置/区域的解释        | 复用旧地点、新候选或过渡；附理由和来源           |
| 地点 Place          | 跨时间可复用的区域身份             | 同一五金店返回应复用旧身份；名字可修，不等于换ID |
| 访问 Visit          | 对某地点的一次连续到访             | 离开后再来是新访问，不是必然新地点               |
| 窗口/批次           | 调度与共同推理单位                 | 8/16/40秒不是地点单位，一批可跨多个地点          |
| 笔记/档案           | 有来源的名称、描述、属性和不确定性 | 门外所见不能无条件挂到室内                       |
| 修订 Revision       | 新证据对旧解释的追加更正           | 保留当时错误和旧快照，不偷偷改历史               |
| 关系/转移           | 有来源的空间关联或先后经过         | 同场所、相邻、连通、可安全通过不是同一关系       |
| 经历/事件/实体索引  | 更丰富的活动、物品和时序组织       | 有旧原型和计划，当前主链尚未全部实现             |

**五金店例子：**第一次到门前→进入店内→出门→过一段时间再来，可能涉及门前和店内两个区域身份、各自多个访问、很多观察。不能因10个窗口就说进店10次，也不能因看不到最初门面锚图就创建另一家店。

地点粒度允许合理变化，但门前人行道、车道与对侧街角不能只因同一店招可见就自动合并。临时空间片段、永久地点、上层建筑和访问次数应当分开表达。

### 3.5 一次空间更新如何执行

1. **先归档：**保存原图/hash/方向/发生与接收时间；后续模型失败也不删原件。
2. **独立提取：**不给历史地点和问题，逐观察生成可见事实；缺项是缺证据，不伪造画面为空。
3. **创建有界工作范围：**调度把已就绪来源交单个空间Agent，不并发启动两个相互依赖的空间写入者。
4. **判断连续与变化：**优先核对前一段延续，新建需正面变化证据；转头、光线和弱匹配本身不证明换区。
5. **检查历史：**召回只提供候选，按需读地点/时间线、查看当前与历史原图。正常VLM模式由主Agent认证；最后ULVN实验改变非连续重访认证权，二者不是同一个算法。
6. **提出操作：**known/new/过渡、名称/笔记维护及未决；多片段按实际来源顺序覆盖，不编造批内时间。
7. **程序验证：**检查ID、来源实际交付/查看、时间、成员与协议。不合法给有限具体反馈，不能偷偷替换成正确答案。
8. **事务与回执：**长期提交成功才发布，并向同一Session返回真实地点/访问ID和版本；失败不假报成功。
9. **工作记忆与修订：**轨迹保留，达到预算压缩；迟到证据追加修订，不将后来知识倒灌早期快照。

因此完整空间更新不仅是一次图片描述，还包括历史候选、工具续轮、证据校验、持久事务、Session和失败处理。模型输出短并不代表整个流程便宜。

### 3.6 一次用户提问如何执行

后期目标不是让空间Agent顺便回答，而是独立问答：

1. 固定发问边界时已经发布的空间版本，以及实际可用的观察/事实截止。
2. 组合只读空间模块与用户自己的私有对话，不静态复制整个空间Session。
3. 当前问题按需看最新原图；历史问题自主检索、读事实，必要时inspect对应原图。
4. 候选预览、完整文字、原图查看和最终引用分别记账，搜到条目不等于已看图。
5. 回答必须对应所问时间、对象和场所，不能拿当前洗衣店回答最早店铺。
6. 问题、调查解释和答案只留问答会话，不成为下一轮观察事实。

新分层实现还提供空间版本0时提问和独立并发额度，避免空间任务卡住就完全不能回答当前画面。该机制有实现/回归，不等于新底座真实长历史问答质量已经通过。

### 3.7 VLM、检索、几何和程序分别做什么

| 方法                         | 实际用途                                     | 收益                                 | 边界                                       |
| ---------------------------- | -------------------------------------------- | ------------------------------------ | ------------------------------------------ |
| VLM                          | 感知、区域解释、候选比较、工具决策、语言回答 | 利用文字/布局/历史语义               | 实例误认、旧状态残留、反例消解和操作不一致 |
| 传统特征/学习描述子          | 从历史找可能关联的来源                       | 比全库逐个VLM比较便宜                | 背景/装修相似不是身份，候选也会漏          |
| SuperPoint/LightGlue＋RANSAC | 核验局部图像对应                             | 能找到跨视角锚点、拒绝部分泛语义匹配 | 独立图对拟合不等于统一位姿或同占据区域     |
| 访问序列/连续提示            | 说明近期经过和连续背景                       | 减少无端new，组织移动经历            | 可能无限扩张上一地点，吞掉短暂返回         |
| 拓扑/位姿侧车                | 组织经过或计算已知几何路线                   | 已知几何交程序，不让语言模型重复算角 | 无真实定位和通路依据时不能变成安全导航     |
| 程序协议/存储/调度           | 校验来源、时间、权限、事务、容量和回执       | 可审计、可恢复、不伪造成功           | 结构正确不能替代语义正确                   |

ULVN相关工作分匹配后端、官方固定图RAVEL/BPL和本项目增量/提交适配，任务前提不同。GPS/现成地图截至暂停只是讨论方向，不属于已经运行的算法。

### 3.8 为什么短期Context与长期记忆必须分开

全历史常驻prompt会增加费用、时延和旧场景污染，只保留最近几条又失去长期能力。因此采用：

- **短期工作记忆：**当前任务、观察、位置、近期判断、活跃未决、工具轨迹和检索线索；有界、过期、可压缩。
- **长期空间记忆：**原图、事实、地点/访问、来源、修订与完整交互；耐久保存，按需检索，不因Context压缩而删除。

空间和问答各有独立Context。新会话从空Context开始；故障恢复要核验同一Session的耐久检查点，不能新建会话灌一段摘要就称已恢复。实现曾从程序摘录视图演进到持续Pi Session主体，不能把最终方案倒写成V1已经完成。

### 3.9 实时、覆盖和时间因果是不同要求

| 概念              | 含义                                | 不能混成什么                   |
| ----------------- | ----------------------------------- | ------------------------------ |
| 输入实时          | 按节拍进入，不等Agent完成才发下一条 | queue拖慢输入但最终跑完        |
| 处理新鲜度        | 最新判断距离最新输入的落后程度      | 输入没丢就等于位置判断最新     |
| 空间覆盖          | 实际判断了哪些观察，跳过/缺事实哪些 | 归档813就等于理解813           |
| 源时间            | 画面发生顺序                        | 模型返回时间                   |
| 可用时间/提交序号 | 事实/版本什么时候真正发布可读       | 整批末尾才知道，算作批首就知道 |
| 恢复              | 同一会话、来源和事务可核对续接      | 另建聊天灌摘要                 |

归档、事实就绪、空间首次解释、修订完成和答案交付应分别报告。单空间writer避免冲突，不自动解决过载；内存、耐久待办、请求轮次和源跨度都要有上限。忙时可跳过调用机会，但不伪造位置，也不把缺口算作全覆盖。

### 3.10 最初目标：场景理解与请求式视觉助手

早期系统围绕SceneAgent、SceneChangeAgent、请求Agent和运动模式输入：当前环境是什么、有没有发生变化、用户问当前画面时如何给身体相对方向的回答。手机浏览器承担相机、传感器、语音和权限交互。

这时的主要工作是闭环原型，而非完整长期生活记忆。

### 3.11 随后：地点、访问与可修订空间记忆

移动后问题不再只是“这是什么房间”，而是：是否仍在原地、是否进入新区域、是否回到旧地点，以及旧判断如何纠正。由此引入地点节点、访问、转移、连续分组、历史候选和可撤回修订。

一个关键认识逐渐固定下来：**观察没有匹配到旧地点，不等于证明换区或从未到访。** 转头、遮挡、光线和视角变化不应该机械触发new。

### 3.12 中期：从空间模块走向生活助手

产品任务扩展到当前视觉、历史回忆、找物、目标关注和自然语言帮助。10月20日产品审阅指出，仅提高空间记忆分数不足以形成可用助手，还缺意图/任务管理、打断、取消、播报仲裁、时效、隐私和真实用户验证。

因此产生桌面Assistant编排、真实相机闭环和独立问答。找物没有被排除出长期目标；但“物品最后记录在哪里”和“物品现在仍在那里”必须区分。

### 3.13 后期：观察、空间维护与问答解耦

真实数据和失败表明，直接把历史解释混进当前视觉，会造成旧场景压过新画面。最终目标逐渐明确为：

```text
原始三摄观察耐久归档
  → 无历史的独立感知事实
  → 持续空间Agent：当前位置、连续性、重访、维护与未决
      ↔ 有界、可压缩的短期工作Context
      ↔ 长期地点／访问／原图／来源／追加修订
  → 固定版本的共享空间模块
  → 独立、只读的用户问题Agent
```

问题、答案、调查解释、裁判意见和位置真值不自动写成观察事实。空间Agent即使没有用户问题，也必须持续维护空间状态。

### 3.14 最后的收敛：不要让视觉独自承担全局定位

11月10–11日的重访失败把注意力集中到“实例身份和实际占据区域”这一基础问题。局部几何可以找到真实图像对应，却可能把不同地点的重复结构或共同背景当作同地；VLM可以口头识别same，却在最终操作里new或归到其他宽区域。

用户随后提出GPS＋地图约束室外、其他算法处理室内的分工。暂停发生在这一认识形成之后，而不是GPS融合已经实施之后。

### 4.1 V1.0：手机上的场景感知与请求式助手

**阶段：10月3–4日，正式保存为v1.0.0。**这一版首先解决“让用户能把眼前画面交给助手，并收到回答”，不是可靠的长程空间地图。

**系统如何工作：**手机浏览器取得相机/传感器和语音输入；场景识别模块解释画面、场景变化模块比较基线并决定是否值得进一步分析，请求Agent按用户问题使用当前图和可选记忆组织答案。身体相对方向约束让回答更接近“你的左前方”，而不是难以直接使用的图片像素坐标。

**这一版做成的东西：**可以交互的手机前端、模型后端和基本图像记忆。初代的场景、变化、请求职责存在，但尚未形成最后那种独立感知—持续空间—只读问答的完整分层。

主要进展：

- 建立场景识别、场景变化和VIO运动模式输入的原型。
- 新增RequestAgent和图像记忆，项目命名为First Sight。
- 完成iOS/Android手机浏览器兼容、证书分发和相机/传感器权限流程。
- 场景变化先尝试图像配准和像素检测，随后明确其只能作触发/提示；变化语义仍由VLM判断，只有确信无变化才跳过模型。
- 请求式回答采用身体相对方向，而不是图像坐标；增加语音输入/输出和可选记忆检索。
- 发布`v1.0.0`，是可交互原型保存点。

阶段认识：传统局部算法可减少重复调用，但检测到像素变化不等于理解有意义的环境变化；多Agent各自工作也不自动形成统一的长期记忆。

### 4.2 V1.1-test.1：从场景描述变成地点与访问记忆

**阶段：10月6–10日。**V1能描述当前场景，但用户移动后还需要知道“仍在原地、到了新地方、还是回来过”。test.1把地点身份和访问历史变成显式对象。

**系统如何工作：**按时间接收多视图观察→利用上一地点、访问/路径和视觉信息提出旧地点候选→SceneAgent比较当前与历史证据→输出连续、已知历史、新候选或未决→程序维护地点节点、访问和转移证据。运动摘要帮助组织候选，不代替绝对定位。

**相对V1的实质变化：**记忆不再只是若干旧图片，而开始表达“同一个地点被多次访问”；判断可以后续修订，未知身份也不应把实际观察删掉。主要验证环境转为可控模拟器，而不是已经在手机真实长途行走中验收。

主要进展：

- AI2-THOR/ProcTHOR episode采集与回放入口。
- Place Memory保存地点节点、访问和路径转移；SceneAgent不再只独立看一帧，而是使用候选缩小比较范围。
- 运动摘要加入定性移动、绝对航向、边方位和expectedNext等信息；明确这些并非原始IMU融合或精确定位。
- 评测引入地点准确/纯度、重访一致性和转移图F1等不同指标。
- 历史原图和多帧输入接入；通过反过合并提示防止把同类环境认成同地。
- 冻结`v1.1.0-test.1`，可修订身份、暂定连续和历史复用成为后续持续讨论的来源。

困难：图和运动提示可以组织候选，却不能补出没有观察证据的物理身份；路径序列也不能自动证明安全连通。

### 4.3 V1.1-test.2–5：连续组、边界和单图附注的四次收敛

**阶段：10月11–14日。这几版是研究协议/算法快照，不是四次实机产品发布。**核心问题是：历史图像匹配失败后观察是否仍有当前归属，以及门口混合视野怎样表达，才不会一会儿全拆碎、一会儿把邻室合成同地。

| test.4 | 固定边界区域v1：组可有主体或边界，并引入单图边界覆盖；配套密集视频审核                 | 尝试显式表示门槛/过渡，而不是强选一侧                     | val4核心44/44，但val5为22/28；4项缺引用、2项单图边界未知，说明跨样本不稳定 |
| test.5 | 固定主体＋单图附注v3.1：整组有唯一主体/边界/未知，单图异议独立保留，不轻易取消主体     | 修正“只因某帧看见邻室就撤销整段身份”的副作用            | val5两次核心28/28；边界/靠近附注仍波动，开发路线和标签不能证明泛化         |

**这一阶段形成的系统形态：**输入时序图像→形成可修订连续经历组→用原图决定组的主体/边界/历史关联→保存组级判断和单图异议→在网页上对照视频和标注。不是把每帧独立分类后简单投票，也不是只有最后的聚类结果而丢掉修订过程。

主要进展：

- 冻结分组验收契约，采用fail-closed配对评测，避免只挑成功图。
- 将时间连续归类真正接到输出，区分当前观察有归属与历史身份已确认。
- 探索可选回溯修复、整组聚合、边界组、单图边界与主体附注。
- 建立人工运动视频/单图审核网站，保留原预测与复核信息。
- 逐步冻结test.2、test.3、test.4、test.5；旧协议、失败和原始分母保持可追溯。
- 准备头盔兼容和广角相关接口，但不把接口准备称为真实佩戴验收。

典型结果：早期val4正式对照中，未归类比例从68.2%降到0%，但跨区域错合并从0/703升到13/703，出现2个混合组。**提高覆盖并未自动提高正确性。** 后来test.5的val5两次核心结果均28/28，但只是相近开发路线、助手开发标签，边界和附注仍不稳定，不能当作跨环境可靠率。

重要教训：

- “同类房间”不等于同一个房间。
- 当前归属、连续性、重访身份与边界是不同问题。
- 单图看见邻室不能自动撤销整段主体，也不能把边界中的多个区域硬压成一个确定身份。

### 4.4 长期记忆v1与V1.2：可持久存储、主动取证的空间问答系统

**阶段：10月15–19日，最终固定为v1.2.0。**它解决的不是再加一种分组，而是让观察、地点和交互真正长期保存，并能在以后发问时读回。

**存储架构：**原图在文件层保存；SQLite分开存观察、归属、地点、访问、转移、模型输出与修订；后台worker处理有限窗口，分页API读库，事务保证修订和undo不会留下半份状态。模型不默认接收全库。

**推理架构：**窗口原图＋有界短期Context→VLM先给当前assessment，再选择结束、search、inspect或answer→实际读历史原图后续轮→长期提交成功后更新Context。此时空间与问答仍曾共用统一循环，不能倒写成已经具备后期两个独立Session。

**相对test系列的实质变化：**研究中的分组/修订开始具备持久服务形态，历史问答需要真实取证，不只是把预先选好的正确图交给模型。旧地点移出短期Context后，可以通过长期检索再获得，而不是无限扩大prompt。

实现进展：

- 长期拓扑SQLite worker、索引、事务修订和持久undo；不依赖无限聊天历史保存一切。
- 受范围约束的检索、原图读回、RequestAgent接入；SALAD等局部视觉召回适配与图像hash缓存。
- 生成当前/短期/长期90题，并执行三条件、因果隔离和独立评分。
- 网络失败重试、未知费用预留、监督进程、Windows退出码和恢复流程逐步补齐。
- 区分算法实际retriever与给定正确参考图的oracle，避免用oracle成绩代替自主检索效果。
- 增加统一空间判断/Context/检索控制循环，短期Context显式有界、过期后重新取证，原始交互可追溯。
- 发现模型已找到候选却反复search，针对取证阶段引导inspect后再回答。

完整问答实测：`run/inspect-repair-full90-v1`从空记忆处理851观察/278事件，90题全部回答、87满分/3零分，能力卡96.67/94.12/96.39；393次HTTP请求，估算USD0.5251330536。这个成绩后来随V1.2被保存，但明确仅适用于该静态开发集、同模型族自动评分。

即使高分，也已出现三类后来反复出现的问题：

1. 看了正确原图仍误认场所并编造细节。
2. 用相似地砖墙裙断言同一楼层。
3. 对关机未记录时段无依据声称一直在同一建筑。

用户接受这些已知限制后固定V1.2；**接受发布不是上述问题已经解决。**

### 4.5 V2形成期：从离线空间模块走向真实采集和桌面助手

**阶段：10月19–21日，属于V1.2之后、V2冻结之前的产品化工作。**离线90题无法说明一个人拿着相机移动时能否使用，所以新增真实输入、生命周期和交互界面。

**系统变化：**原始相机适配与采集放在硬件层；桌面服务负责会话、任务和回放；空间先持续生产，用户问题读取已有记忆。用户不必先提出问题才让系统开始记录环境，问题也不必重新构建一次空间库。

**与V1.2的区别：**重心从离线控制循环变成在线输入/前端/会话的组合，并开始正视“什么时候说、怎么取消、答案是否过时”等产品要求。这些要求被识别不等于全都实现。

主要进展：

- ESP32-S3相机验证固件、串口采集、UART提速及约2秒采样验证。
- 三摄Wi-Fi和模拟光学准备，但尚无真实同步/标定证明。
- 建立桌面浏览器Assistant、视频回放、文本诊断、视觉目标任务和语音文本交付。
- 空间生产与问题回答逐渐分开：先建空间、问题只读固定快照，避免每次提问重新生产空间记忆。
- 形成6条更贴近真实交互的故事；放弃只靠模板90题定义产品能力。
- 校园原生视频、空间结果、问题时间和回答同步展示。

产品审阅提出的关键缺口：任务生命周期、取消/打断、静音与停止采集分离、播报仲裁、过期答案、用户纠错、隐私与删除，以及真实视障用户的参与。

这一阶段确认：**空间记忆只是生活助手的一项能力，不是完整产品的同义词。**

### 4.6 V2算法基线method2：固定范围原图比较与访问序列

**阶段：10月21–23日。**这一版试图解决候选随意漂移、只看单张代表就认同地的问题，并与真实相机输入连接。

**算法如何工作：**独立感知当前画面→从近期地点和视觉召回获得有界候选→核对候选组固定范围内的成员原图→利用最近访问序列决定延续、复用、新建或未知→存入实时记忆。典型入口使用recent2/visual2候选与recent6访问，不是把全历史图关系都塞给模型。

**为什么称method2基线：**曾将近期序列与拓扑图context分臂比较，图提示未稳定胜出，最终保留sequence-first。保留访问转移数据不等于恢复已放弃的guarded-graph决策方案。

**收益与代价：**固定scope和原图比较提高证据可审查性，但组成员增长会增加分页比较次数。后来的EgoLife失败表明，该成本不是可以忽略的实现细节。

算法工作：

- 尝试原图身份比较，失败后降低协议负担，进一步分离当前感知和身份动作。
- 固定scope、全成员分页比较与证据来源检查，防止只凭一张锚图做宽泛合并。
- 候选由近期访问＋视觉召回有界提供；历史序列与拓扑图context做独立对照。
- 进行重复运行和带预先回退标准的图提示实验；最终保留sequence-first/method2基线，未证明图context稳定胜出。
- 建立HSSD来源边界与空间接受流水线，避免把不同条件数据分数混用。

硬件与应用工作：

- 设备侧扫描、校园portal认证、单摄Wi-Fi图像接收。
- 分解传输时延、比较无休眠/持久连接/JPEG质量，加入积压新鲜度与采样连续性门禁。
- 真相机会话接入method2和只读问答，网页系统开关、记录开关和预览控制落地。
- 后续修正倒置画面、低光配置、自动回放、隐藏回放不删除原件、记录边界和诊断上报。

局限：单次静态连接与收几张图不等于移动网络稳定；全组比较随组增长而增加调用，后来在EgoLife中成为直接吞吐瓶颈。

### 4.7 V2.0与V2.1：真实相机闭环和三摄工程扩展

**阶段：10月23–25日。两次正式冻结侧重点不同，不是V2.1已经全面替换V2.0空间算法。**

**V2.0做成了什么：**单前摄ESP32→主动上传接收→像素等价PNG/特征→method2空间生产者→SQLite因果记忆；用户问题走独立search→inspect→answer。网页控制预览、记录、系统启停和只读回放。相机、接收进程、Node编排和问答的职责开始明确，真实数据而非只有模拟回放进入系统。

**V2.1具体增加什么：**把设备扩为前/左/右三台，使用独立cameraId、方向和配对鉴权，在同一网页展示三路。前摄沿用记录/模型链，左右只作独立RAM预览。它是多设备工程保存点，未增加已验证的空间算法准确率。

**两版共同的缺口：**移动网络不稳定、缺离线补传、IP变化需同步，以及长期供电/同步/标定和真实佩戴未验收。不是修改一下页面就完成全天随身助手。

主要进展：

- 相机HTTP主动上传接通预览/记录/回放。
- 尝试RAM网络诊断、跨重置故障保存、Android热点中继和iPhone热点关联。
- 实际结果不足以解决移动断流，用户停止通信扩展，恢复主动上传基线，保留全部试验和失败。
- 未来UVC三摄＋随身计算机/SSD＋独立蜂窝同步只作方向存档，没有购买部署或假称离线模型可用。
- 固定V2单摄实时原型：真实采集→归档→空间记忆→问题回答，但保留断联、IP变化、无补传、长期稳定性等限制。
- V2.1固定三台摄像头cameraId、front/left/right方向、独立配对及网页预览；短测每路3张640×480图，方向和鉴权隔离通过。

必须保留的边界：V2.1左右摄像头只是RAM预览，尚未进入method2，也未形成持久三视图录制。三路有图不是三摄空间算法全链完成，更不等于曝光同步/时钟外参标定完成。

### 4.8 V2.1之后的并行支线：定位、路线与生活记忆参照

**阶段：10月25–27日；不是新的统一产品发布。**这条支线探索“已知位姿/路径怎样用于记忆和语言帮助”，与硬件V2.1和后续纯视觉主线不能混成一个系统。

**分工思路：**视觉识别地点，程序保存已知pose通行经历并计算路线、顺序和方向，说明Agent只负责把已得到的路线写成自然语言。真实IMU/VIO输入、跨会话坐标对齐和人体朝向仍是缺口；已有几何回归不代表实际设备有可靠定位。

这一支线的内容来自Git提交和已有交接文档，本次没有进入独立research工作区重新审计：

- 保存3D-Mem基线、IMU噪声试验、VIO融合退化和旧目标崩溃诊断。
- 转向基于图像的OpenVINS回放，构建driver并记录初始化与噪声条件。
- 核对VLM空间方法实际依赖的pose、深度、SLAM、地图或几何模块，避免把“VLM空间推理”误理解为纯图像自由推断。
- 明确本项目终点是人的自然语言路线帮助，不是机器人action执行。
- TartanGround既有位姿路线侧车形成程序几何/正反向路径与说明Agent分工；74几何、190连续性检查是程序回归，不是190个用户任务。
- 对生活记忆、事件检索、找物、变化和长期视频benchmark做适配审查，逐步不再让某个现成benchmark反过来定义全部产品。
- 将LightMem-Ego作为重要生活记忆参考；没有完成双方公平QA对照。

LightMem对照实际只做到固定源码/环境/权限检查及同3张图的存储冒烟。完整依赖、embedding、共同任务gold和真实生活素材云处理权限未齐，0付费调用，准确率应记“未评测”，不能写成某一方0分或某一方胜出。

### 4.9 评测与输入系统换代：EgoLife失败、UnionCity长经历

**阶段：10月27日至11月1日。这是输入/评测基础的转变，不是声称产品又发布了一版。**核心原因是静态校园题无法充分暴露短事件、室内外转换和多次到访，必须检查系统在真实节奏下究竟记录和理解了什么。

**新的数据工作流：**真实生活视频用于暴露采样/建忆/检索缺口；可控UnionCity路线用于检查地点、动作、时间、原图与历史身份。原始图、公用输入、评测标签/位置和模型结果分别保存。这样才能区分“没有拍到”“拍到却没建忆”“有记录但没检索到”和“看见证据仍答错”。

这段工作大量存在于历史同步和本地资产中，不应仅因Git日期空档而漏记。

**EgoLife先导：**

- 原生RGB链路按官方前10题真实执行，结果0/10、全部拒答。
- 下载136段原片约1.744GB，2033帧原图归档，但实际完成建忆只有90帧；第10题截止仅89条判断可用。
- 1073次调用，其中993次建忆、80次问答；估算USD0.4092848736，非预算耗尽。
- 空间全组分页比较占建忆调用约89.3%，有效建忆间隔中位44秒，最长142秒。
- 有一个约8秒的二楼到访：2秒归档图已拍到桌面和物品，但空间建忆一直忙，最新帧队列跳过了这段到访。**不是简单“原图没采到”，而是采到了却没有成为可定位的事件记忆。**
- 原生检索主要索引地点/name/region，无法充分检索物品、人物动作和事件；问答重复search或inspect未交付ID。
- 首10题音频/名字需求与纯RGB输入明显不匹配，但不需音频的题也失败，不能把全部失败推给数据集。

**UnionCity与可控素材：**

- 为获得连续室内外移动、门口、店铺、楼梯、公寓、电梯、回访等可检查场景，转向GMod/UnionCity。
- 用户手动路线记录后生成383组三摄的首轮重渲染；首次method2试跑20分钟只完成33/192采样观察，146调用，尚未进入首个返回测试。
- 经修复形成最终813组三摄：不是简单改时间戳或图像插帧，而是沿原轨迹插值相机并重新渲染。
- 原源时钟约405.555秒，授权展示时钟约811.110秒；后续2秒投递又有显式回放工作时钟，不能混作同一个时间量。
- 36次E按下/36次释放、已知目标重放、电梯轿厢/门/灯同步和错误目标拦截均单独留痕；不是完整物理行走/动态世界重演。
- 最终813组、2439张三摄图、42访问段、35区域ID、3显式重访，建立原图/位置参考/公用输入/私有评测的隔离。

主要成果不只是“找到一个游戏地图”，而是建立可重复、可核对输入时刻、方向、动作与参考边界的数据资产。它依然只有一条开发路线，重复建筑资产和受控生成会带来偏差，不能代替真实生活泛化。

### 4.10 因果问答与组织/调查原型：历史信息必须真的被找回

**阶段：11月1–2日，包含多条显式实验配置，没有统一正式版本号。**这一版针对的是“问答看似正确，但根本没证明用了长期记忆”。

**系统如何工作：**共享视觉事实持久库→近期有界Context→独立问题分支；历史内容只有调用工具后才交付。另建组织库，把事实按候选经历及追加修订组织，再让调查Agent沿timeline/read/find/around/inspect自主取证，输出当前调查报告，不回写成已认证观察。

**相对method2问答的变化：**不再预先把全历史相关信息塞给问题Agent；显式区分当前图、短期事实、长期检索及真实原图引用。组织器和调查器是可选配置，不代表所有线上入口已经迁移。

**因果90题：** UnionCity当前/短期/长期各30题，公共问题与私有答案分开；初始只给当前图和约60秒独立事实，长期信息必须主动检索。

实际813事实全部完成，90题执行、87交付/3失败；自动初评当前96.67、短期82.50、长期74.17，总84.44。但审核发现：

- 自动裁判漏掉“可以直接走进去”等无依据安全承诺；
- 重访把答案重新带回近期Context，导致长期资格污染；
- 查过库却引用无关历史，最终仍用当前场景替代最早店铺；
- 示例中的固定时间边界被照抄，错误限制搜索。

因此只保留开发初评，不给“最终准确率”。

**组织与调查：**

- 保存独立组织SQLite，原事实不变、修订追加、双重时间截止、只读问答。
- 旧事实启发式构建先得到2段、再23段、后21候选段；这些数量不是物理地点真值。
- 增量同步、启动对账、幂等及51前缀/5次重开验证通过，但仍非语义事件索引已可靠。
- 原15题/37分支组织pilot仅36/37交付，正常15题效用50%、7/15达到≥3，冻结门槛失败。
- 从`locate`词项函数转向调查Agent；随后用户拒绝专用计数/序数路由，保留通用timeline/read/find/around/recall/coverage/inspect。
- 通用7题pilot全部交付，但“最早店铺”和“以前休闲场所平台”两题仍不调查，直接用当前洗衣店/屋顶回答。

**Pi与历史污染：**

- 将持续空间轨迹交由Pi Session管理，并为问答维护独立会话。
- 压缩输出截断、框架默认fallback和无工具摘要请求造成故障，后来补fail-closed、有界反馈与独立恢复文件。
- 一轮813全部完成且结构审计0错误，却把最初站台未决点重复保留到802条更新；另一90观察短测到街道仍描述旧柜台和绿桌。
- 独立当前感知fact-first缓解旧场景压过当前视觉，但空间解释仍会把相似瓷砖和灯具推成同楼关联。
- 进一步区分“历史曾经读过”与“本轮实际交付/可引用”，清空跨观察召回权限而不删除长期原件。

11月2日建立active设计依据与TODO状态分工，重写空间判断/Context/长期检索主干，避免“最近几条事实”被当作完整架构。这些原型中的有用契约保留，但不能原样恢复已经被否定的题型路由、计数协议或仅靠词项的“智能定位”。

### 4.11 持续空间底座版：Pi Session、8秒窗、地点访问库与事务

**阶段：11月3–4日。它是空间主链的重要重构，不是仅调整采样频率。**目标是让空间模块在没有用户问题时也持续判断、调查、记忆和维护，而不是每次问题临时拼背景。

**系统如何工作：**耐久原图→独立当前事实→持续Pi空间Session→有来源assessment/工具调用→`memory_add`事务→地点/访问/笔记/修订→真实回执与检查点→只读问题视图。8秒窗口共同解释最多4次观察，长期证据逐次保留。

**相对组织/调查原型的变化：**空间位置是必须维护的显式状态，不再只是事实描述或后置检索报告；短期记忆以持续Session为主体，长期库按地点/访问组织，程序负责可靠执行，模型负责有来源的语义操作。

主要实现：

- 以8秒窗口共同解释最多4次2秒观察，保留每次原图和事实，不复制成4次独立定位。
- 独立提取与单空间写入流水重叠；迟到证据、缺口和追加修订分别记账。
- 持续Pi Session保存输入、输出、工具与失败；模型预算触发压缩，结构状态头仅用于发布与恢复。
- 地点档案、属性/名称修订、笔记与来源，形成`memory_add`事务和`memory_place`地点→访问→窗口→原图读取。
- 同一地点多次访问保持同placeId、不同visit；真实提交结果回到Session。
- 校验known必须有实际历史取证，补交付图而非自动替模型认证；修复地点UUID/观察ID混用与字段级反馈。
- 恢复时核对Pi、SQLite、skill/hash与检查点，不伪造Session或重复模型推理。
- 恢复本地视觉重访候选SIFT/RANSAC及缓存，明确候选不等于身份。

测试从500余项逐步增加到586项以上，覆盖大量事务、来源、恢复和协议路径；真实模型仍暴露测试桩没有覆盖的图数cap、遗漏事实、非法引用和纠错循环。

首次813空间生产在`unioncity-memory-full813-v2`经两次resume完成：813观察、204状态/Context/Pi检查点、0缺失/跳过/pending，16地点/23访问/84笔记。它是失败修复后续跑完成，不是一次干净运行；perception240调用、Pi317调用，累计估算约USD1.242。

这轮显式queue回放有大量背压，不能作2秒实时认证。历史865.86秒是对应收据的阶段口径，不应当成包含此前失败/停止的全部项目墙钟。

质量仍存在：当前理由照抄旧窗、门口混合窗偏向尾帧室内、路口整窗归属过宽、OCR及物体用途推断进入笔记和摘要。

自动整体裁判也出现问题：Max两次给100分，却放过原图不支持的旧理由。后改为“盲看原图→逐项对照身份/理由/范围→综合”，有争议不发布可接受总分。Flash与Max严重度不同，不能把换裁判后的降分当作被测系统退化。

### 4.12 强制实时／16秒窗版：用显式缺口代替拖慢输入

**阶段：11月5–7日，是持续空间底座上的运行策略与效率改进。**此前queue可以保持最终全覆盖，却可能把实时系统变成等Agent的离线批处理。

**系统变化：**归档按源节拍继续，空间只有一个写入者；忙时跳过新的调用机会，保留原图/事实给后继检查。输入进度、判断覆盖和缺口分别报告；缩减重复上传和压缩阻塞，允许有界纠错，但不伪造跳过窗位置。

**这一版解决什么：**第一次把“输入有没有被拖慢”作为独立硬验收，而非以最后跑完为准。16秒配置改善吞吐，但带来7窗未判，不能称813空间完整覆盖。

关键改变是重新定义实时验收：**按源节拍投递，不为等Agent而拖慢输入。** 忙时跳过调用机会、原图和事实保留，缺口不算已判断覆盖；不能把无限队列或延迟投递叫实时。

这一过程中有六次813尝试失败：机器休眠、证据循环、非法压缩摘要、窗口乱序跳过破坏前缀等。失败原样保留，不把所有失败都叫模型能力问题。

实际优化包括：

- 跳过立即释放容量，后续结合skippedBefore来源；
- 当前图首轮交付、减少重复图上传；
- 摘要后台预取、提交边界拼接而非阻塞每轮；
- 可选字段本地失败处理、known证据紧凑纠错、连续失败计数；
- 量测提取/判断/提交/封窗时延和重试分布；
- 试验流式提取，但96帧通过不等于813通过，未把失败配置定为默认；
- 16秒窗成为显式测试配置，不取消单空间Agent职责。

11月6日首次强制实时813运行完成：95判断窗＋7跳过窗＝102计划窗，空间覆盖757/813（93.1%），0投递违规、最大滞后428ms、0背压。**这是输入实时通过，不是全813空间覆盖。**

11月7日约束评分为系统as-run74.7；排除未测重访维度后87.0，后者不能代替系统总成绩。匹配器超时造成大量窗口没有候选，应该标未测而非当作Agent拒绝了所有返回。

这一阶段明确：单纯放大窗口不一定提高吞吐，因为图像数、提取与判断工作量也会随窗增大；必须减少重复工作、隔离关键路径并处理长尾。

### 4.13 6秒感知／40秒多片段版：降低重复看图成本的分层系统

**阶段：11月8–9日，是暂停前最重要的完整实时VLM基线。**16秒窗仍容易让图片理解、空间维护和工具长尾绑在同一个频率上，所以改为快速感知与较低频空间巩固。

**系统如何工作：**约6秒的无历史感知先产出逐观察事实；约40秒交一段事实时间线给持续空间Agent，只在需要时读取少量当前/历史原图。空间Agent可在同一批提交多个真实片段和过渡，不能把40秒强行视为一个地点。问答独立读取最新证据与固定空间版本。

**关键区别不是把8/16改成40：**默认输入从整批图片转成事实，原图转为工具按需取证；批内允许多个地点；归档/事实/空间/问答独立调度，保持同一单写入和来源/事务规则。

架构方向：归档、快速感知、持续空间维护和问答分别调度；快速感知约6秒，空间约40秒，默认交事实、按需取原图，一批可判断多个真实空间片段。空间初判/续轮/修订只有一个串行通道，所有队列和耐久待办有上限；问答可在空间版本0启动，不排在空间队列之后。

实现形成分层runtime和另一条与旧Pi行为对齐的40秒批次运行路径。不能仅凭名称将两条入口当作同一个受测系统；实际基线manifest指向原`run-spatial-memory.ts`的Pi v2批次路径。

离线验证曾记录628/628、后642/642通过；模型请求是桩，包含真实Pi/SQLite/工具行为，不能认证真实VLM空间语义。

真实完整基线`run/unioncity-batch40-realtime813-v1`：

- 813/813归档、独立事实和空间覆盖；41批次，69状态/Context/Pi检查点。
- 17地点、25访问；这些是模型产物数量，不是独立真值数量。
- 0跳过、0缺事实、0判断失败、0背压。
- 2秒投递最大滞后205ms，0违规。
- 总1641.833秒（27分21.8秒），估算USD0.38124，无未知预留。
- 封窗→提交p50=25.611秒、p95=66.055秒、max=70.734秒。**完整输入节拍通过，但并非每批判断都小于40秒。**

成果是实质性的：在该样本、该模型和调度条件下，完整持续记忆系统能跟随输入完成全覆盖。

但后续质量审查并未放行可靠重访：整体自动序数分90/100不是精确率；参考对齐、实际返回事件、原图语义和不同区域粒度产生多个不一致结论。进一步追查发现，旧地点候选虽然在清单里，却可能没有实际预载/检查；上一地点连续性又会吞掉批内短暂返回。

### 4.14 重访增强实验版：修证据交付与同地核查，未形成可靠替代

**阶段：11月9–10日。**完整40秒基线能运行，不代表每个短暂返回都被正确恢复。本阶段只围绕这个问题做有限对照，不是另建一套已发布产品。

**系统变化：**视觉检索保留真实当前/历史图对与方向，首轮预载有界证据，时间卡绑定来源，主Agent显式核查same/different/insufficient后再提交空间片段。不同提示词与图对预算在固定背景下重复验证，避免单次碰巧成功。

最后集中Git保存点为`a272a69`；其后结果与修复仍在未提交工作区。主要发现是即使局部checks认可同地，最终持久身份仍可能不一致，不能只靠增加一句提示解决。

工作重点：

- 当前匹配查询从批首尾扩为批内全部观察三摄。
- 确保inliers和similarity来自同一个真实图对，保留实际当前/历史方向，不再拿匹配到的旧left图换成旧front图。
- 2/3/5图对预算、时间证据卡、来源绑定、显式same/different/insufficient核对、连续性锚图等有限对照。
- 每背景重复3次，避免凭单次随机成功选配置。
- ULVN相关后端接入MegaLoc＋SuperPoint/LightGlue，实际CUDA运行；与legacy的前端及下游固定背景比较分开。

v10下游18试验均协议合法，旧后端目标恢复8/9、新后端5/9；不能直接推出legacy语义更优。后续发现模拟器交付raw召回、生产只交投影，以及旧图对说明与新图片不一致等混杂，原结果只能作诊断。

按用户设定的最后两轮限制完成后，没有稳定达到整体要求。进一步从v57错误源头隔离三套提示词，各两次、源头/后续/真同地共18阶段，没有一组两次完整通过。能看见差异却仍用共性和视角解释确认同地；正例checks说same，最终segments却new或引用未交图。

结论：**本轮提示词不足以使当前模型、输入方式和预算下的身份/分组可靠。** 不是证明所有VLM理论上不行，也不把测试交付问题全算作模型能力上限。

### 4.15 ULVN路线的三种系统：固定图、增量探索与完整Pi集成

**阶段：11月10–11日。**目标从“换一个候选后端帮VLM”推进到实际检验“不让VLM做最终重访认证是否可行”。三条试验不能混成同一个版本成绩。

| 试验系统           | 输入/内部机制                                          | 输出                        | 与前一主线的关键区别                                    |
| ------------------ | ------------------------------------------------------ | --------------------------- | ------------------------------------------------------- |
| 官方RAVEL/BPL      | 参考图先建固定节点图，顺序查询更新belief               | 已有节点上的位置/质量       | 不依赖VLM，但没有本项目所需开放集new/增节点完整接口     |
| 本项目顺序增量适配 | 当前/过去三摄，视觉候选/几何，额外连续/new/revisit策略 | 增量节点/组与暂定身份       | 从空库探索，但新建/锚点/连续规则是自定义适配            |
| VLM＋ULVN直接重访  | 正常VLM持续维护；ULVN给非连续历史身份，工具内投影      | 真实Pi/SQLite地点访问与回执 | 不仅前端候选变了，最终重访认证权变了；常规VLM职责仍保留 |

“ULVN”在本项目里必须分三种东西：

1. 本地MegaLoc＋SuperPoint/LightGlue＋几何核验的实验匹配后端。
2. 固定官方commit `e2f47fe`的RAVEL建图＋BPL定位实测。
3. 为本项目顺序新建/连续/重访和Pi提交增加的适配策略。

不能把第1种前端替换叫完整官方系统复现，也不能把第3种策略失败全部归于官方算法。

**官方固定图实验：**

- 全程预建102节点、711留出查询，自动标定后图0边，实际0次几何验证；默认标定/检索范围退化，不能称拓扑成功。
- 因果前缀41节点、492后续查询，14边/27分量；固定节点BPL无unknown/new/在线增节点接口，不能原样承担开放集持续探索。
- 预建图在物理200/400单位条件下78.3%/86.7%，但有全程地图和邻近轨迹参考，不可与空历史VLM持续建图横比。

**空库顺序适配：**

- v1全813、369.663秒、107组/158节点，三个已知返回同组；全组审查发现当铺/露台、餐厅/街道等误合并。
- v2全813、936.873秒、67组/140节点，4个旧错误控制分开，但222观察身份暂定；固定首锚点和6次暂定上限又阻断正确连续/返回，用户明确不接受这种拆分依据。
- 后转向只做重访，不强迫无匹配输出new；保留正常连续性与真实原图。
- 最终9查询收束诊断找回3个指定返回，拒绝7个强制检查的旧错对；仍发现共同背景不能认证精确占据区域，因此不把开发控制全过称全量可靠。

**完整Pi＋ULVN直接重访模式：**

- 用户批准仅替换跨历史重访认证权，保留原VLM感知、连续/新建/边界、短长期记忆、事务和问答隔离。
- 第一轮轻量因VLM与ULVN权威冲突失败；后改为真实`memory_add`工具内机械投影身份，再走原校验/事务/回执，不靠后台改库。
- 纠错轻量139/139、26状态/Context/Pi检查点、0缺失/跳过，910.756秒。
- 完整813轮运行约70分03.8秒后中止：只归档484、空间覆盖420，21批/64状态；没有完成全量。

速度问题主要不是ULVN天生必须很慢，而是把离线诊断预算直接逐观察串行接入：一批最多20观察×20历史候选×9图对＝3600核验上限，还重复hash/IPC/特征和整批重试。已提交阶段约68%时间在首次重访计算、27%在空间VLM；使用quality/queue又把积压变成延迟投递。

### 4.16 独立有限域加速版：让重访模块计算可用，但未解决身份歧义

**阶段：11月11日。**完整集成中止后，先脱离付费VLM测计算瓶颈，而非继续让用户等一轮全系统。该实验读取已有生产地点目录，只按因果前缀使用，不是新的空库全功能产品。

**系统如何工作：**每张图编码一次→每个历史地点取视觉多样代表→全局检索少量可能域→在代表附近有界补查原图→双独立方向几何门禁→输出fresh支持或预算未决。同像素图对可缓存，不能命中过一个地点后让所有无关当前画面免检。

**相对密集集成的收益：**减少重复历史编码、全库读hash和成百上千无差别几何；没有通过把所有职责删掉而声称完整系统提速。它只解决独立模块的工作量，未证明最终地点身份可靠。

加速过程不是单向成功，而是一系列保留失败的比较：

| 方案                     | 完整381–400窗耗时 | 质量/工程结论                             |
| ------------------------ | -----------------: | ----------------------------------------- |
| 20候选、1024点密集核验   |          151.263秒 | 保留指定返回，但太慢                      |
| 5候选                    |           31.943秒 | 店内真匹配在第9位，被裁掉；速度不能算无损 |
| 20候选、512点            |          160.148秒 | 通过减少、早停减少，核验次数反增且漏认    |
| 多样代表图＋地点共享调查 |           20.194秒 | 存在代表覆盖不足和整地点免检缓存错误      |
| 代表图＋有界局部域补证   |           24.992秒 | 恢复具体来源，仍有预算未决                |

最终采用每地点最多8组视觉多样三摄代表、代表附近±4个同地点连续观察、最多3域/每域3候选、每查询24次实际几何调用、精确hash图对缓存；不降低60内点/0.35双独立方向门槛。

前420测试255.947秒；全813测试510.994秒，41窗全部低于40秒。全量使用旧完整生产目录69状态/813成员（811有地点、2未知）的因果前缀，不输入位置真值，但**不是纯ULVN从空库自动生成地点目录**。

质量复核之后，结论不再是“速度过了就完成”，而是：地点级审核找回7/8个返回区域，仍有3组明确异地关联和4组占据边界敏感关联。随后讨论较准确定位与室外地图约束，未实施GPS融合。11月16日用户决定暂时停止项目。

### 5.3 负结果本身的价值

本阶段的负结果至少排除了几种过于简单的假设：

1. **“把当前图和历史都交给VLM，它自然会维护正确地点身份。”** 实际出现旧状态残留、共性认证同地与证据—操作脱节。
2. **“候选找到了，就等于解决重访。”** 候选可能未交图、未查看、未引用，或看后仍误认。
3. **“两摄几何通过，就能自动认证旧地点。”** 实际三个明确错对均通过且未耗预算。
4. **“增加上下文/图关系总会更好。”** 图context未稳定胜出，过多历史还会污染当前。
5. **“减少候选/特征点就是等比例无损加速。”** 5候选漏掉第9位真匹配，512点因更多补查反而更慢。
6. **“整体裁判高分就能证明空间记忆可靠。”** 100/90/97等分数都曾掩盖具体来源、重访或范围问题。

### 6.3 最后地点级结果及其证据强度

截至暂停，采用原图视觉复核而非标签相等的记录为：

- 返回目标：8个占据区域，找回7个，**召回7/8＝87.5%**。
- 去重正确地点关联：7组。
- 明确异地关联：3组。
- 共同背景/不同占据区域的边界敏感关联：4组。
- 按不认证跨占据区域的保守审核，**精确率7/(7+7)＝50%**。
- 排除4个边界敏感组后7/10＝70%只是确认子集，不是全量精确率。

这组分数是**助手对全部137接受对联系图及抽样/重点时间线的审查**，不是独立人工gold；地点范围和返回目标分母仍应由独立审核复验。不能把它宣传成具有统计置信保证的最终产品准确率，也不能与旧VLM不同口径成绩直接排名。

此前66/137＝48.18%的标签一致率、52/135＝38.52%的逐观察返回召回，以及100/200/400坐标半径指标，都保留为不同任务的诊断，不再代替上述地点级结果。

### 6.4 为什么没有一个“项目总准确率”

以下各项不能平均或串成同一条进步曲线：

- 当前事实是否被图像支持；
- 当前占据区域是否正确；
- 持久地点ID是否复用；
- 一次返回事件是否至少找到过一次；
- 每一帧是否都有正确匹配；
- 自主检索是否真的取回目标；
- 问题是否答对；
- 是否遵守来源/因果/安全边界；
- 输入投递是否实时、空间判断是否新鲜、是否全覆盖。

项目历史里“高分却失败”往往不是逻辑矛盾，而是测了不同能力；也有真实裁判错误和实现缺陷，不能都用“口径不同”开脱。

## 7. 困难、失败和根因

### 7.1 地点身份：类别、实例、场所和占据区域经常混淆

看到绿色桌子、棋盘地砖、红砖、彩旗、消防栓、店招，能够支持环境描述，但不能直接证明是同一间店、同一路口或同一楼层。

同一建筑内部可有多个区域，同一区域可有多个视角；同一条街也可能允许多种合法划分。问题不应简化为ID必须等于参考或地点数量必须一致。

真正需要拒绝的是：明确不同路口认证成同一具体路口、外面当里面、不同占据位置因同一背景被强认证，以及没有来源的身份确定。当前系统尚未稳定解决。

### 7.2 连续性：既不能每窗重建，也不能无限沿用

- 没匹配不证明离开，不应因首锚点不再可见就拆新地点。
- 但沿用上一位置会吞掉短暂返回、边界和真正换区。
- v2增量方案用固定锚点/6次暂定上限防误合并，又阻断真连续和重访，说明简单计数规则无法替代证据判断。
- 回到旧地点要新visit，而不是新place；片段数、窗口数和进店次数不能互相代替。

### 7.3 观察、历史解释和当前状态污染

最明显证据包括：站台疑问残留802次；front已朝街道仍描述旧柜台；旧理由逐字复制到新窗；检索旧来源的权限常驻到下一观察。

独立观察、固定事实、按轮交付资格、过期未决退出工作视图等工程修复是必要的，但不能靠删除整个空间推理阶段来换取“无污染”。最终空间判断仍需有历史、连续性和自主检索。

### 7.4 检索：存得多，不等于找得到

EgoLife的2033原图/90建忆以及UnionCity的“最早店铺”错误说明：

- 地点索引不足以回答物品、人物和事件问题；
- 词项函数不等于智能定位经历；
- 全局4张均匀浏览可能跳过8秒短事件；
- 同一分页首页反复读取不等于遍历历史；
- 查询词先被当前场景偏置，工具再准确执行，也会得到错误目标；
- 工具调用或引用出现不证明它因果支撑了答案。

这不是仅靠扩大Context就能稳定解决的问题。经历/事件/实体组织和可靠浏览仍有未完成能力。

### 7.5 证据协议与Agent操作一致性

常见故障不是只有非法JSON，还包括：

- 地点UUID填进观察ID字段；
- 提交known却不引用历史原图；
- 已读文字被误当已看原图；
- 检索到候选但未实际交付；
- inspect和提交校验互相拒绝形成有界死循环；
- checks口头判same，最终却new或归其他地点；
- 当前/历史图片没有在需要比较的同轮共同出现；
- 模拟器图片更新后，旧说明和preloadedImageIds未同步。

字段级反馈、真实交付、事务回执和真实Pi回归改善了工程可执行性；但更多程序守卫无法自动把错误语义修成正确事实，也不应后台改库伪造Agent操作。

### 7.6 吞吐与实时：平均快不够，长尾和重复工作很贵

早期全成员分页比较随历史增长放大，EgoLife约89.3%建忆调用耗在历史比较。后期几何匹配又出现20×20×9的批内密集核验，说明无论VLM还是传统/学习匹配，错误的工作量增长都会拖垮实时。

多个短测“跟得上”不能认证813长程，更不能认证全天；平均延迟不能替代p95/p99、缺口、积压跨度和实际投递违规。

需要分开：相机采集、耐久归档、事实就绪、空间首次解释、证据完整、修订完成和问题答案可用。把它们统称“实时理解”会掩盖真实限制。

### 7.7 数据与评测：本身就是一个长期工程问题

- 校园资产存在许可、可达性和场景资格问题，下载成功不代表适合大校园评测。
- HSSD/THOR/ReplicaCAD、Tartan、真实生活视频和UnionCity的传感器/动态/目标差异很大。
- EgoLife首10题多需音频和名字，不能不说明输入缺口；但也不能靠换题掩盖真实吞吐失败。
- 重渲染不是原始视频恢复，电梯/门交互不等于原动态世界完整复现。
- 同家族裁判可能有确认偏向、OCR幻读、严重度不一致、原文quote错误、漏安全问题或把参考额外要求强加给答案。
- 用参考ID粒度直接判错会错罚合法范围；用同地标证明同一区域又会漏罚真实错认。

因此，评测越往后越强调盲取证、原文精确绑定、语义/机制分开和人工复核。但截至暂停，仍缺独立、代表性、冻结的地点身份gold。

### 7.8 硬件与部署：原型可运行，离日常随身产品仍有距离

校园Wi-Fi覆盖、认证、漫游和互访限制、相机掉线、上传不完整、IP变化和电脑休眠都有实际影响。曾尝试手机热点/中继，但没有足够收益，已收束而非持续投入。

三摄设备身份接通只是一步；曝光同步、时钟、外参、持续录制、供电、散热、佩戴和长期容量都未验收。早期VIO/IMU实验或浏览器运动摘要也不能冒充当前持续空间主链已经有可靠定位。

### 7.9 产品与安全：最后所见不是当前世界状态

断拍期间位置和物品可能改变。系统应说“最后记录在……，之后未知”，不能把历史图推成现在仍在。看见门口不证明已经进入，看见可通行外观不证明安全。

目前没有真实视障用户任务成功率、全天可靠性、完整隐私删除和高风险导航验收。原型应保留为研究/开发工具，而不是安全通行保证。

## 8. 最后一轮ULVN重访问题的完整结论

### 8.1 最终加速成功究竟证明了什么

在RTX4060 Laptop 8GB上，固定已有生产历史目录、因果前缀、813查询/41窗，最终完成：

- 端到端510.994秒；平均12.035秒/窗，p95=23.179秒，max=27.564秒。
- 6052实际图对，2017局部特征抽取、10087特征缓存命中。
- GPU已分配峰值约1.69GB，不是整机显存总占用或最低需求。
- 0付费VLM调用。

证明了通过代表图、有限邻域补证、增量编码和精确图对缓存，可以大幅减少无效工作。它没有证明后续完整Pi系统同样快，没有测现场上传，也没有重新跑完已经停止的完整VLM＋ULVN813。

159/813查询触及24次核验上限，其中136无fresh接受；无接受不能当确定没来过，预算耗尽不能算确认阴性。旧`unresolvedPlaceCount=0`在该模式未填，不能解释成没有未决。

### 8.2 地点级复核找回了什么

| 目标区域        | 证据解释                                                               |
| --------------- | ---------------------------------------------------------------------- |
| 当铺门前        | 离开内部后，实际门前历史来源有匹配                                     |
| 公园侧街段      | 返回段中存在真实历史对应，不要求每帧命中                               |
| 餐馆外部        | 进入内部后回到外部范围，多个视角匹配                                   |
| Union现金店街段 | 实际返回街段已有匹配，不能把小巷出口标签差异当整地点漏检               |
| 五金店门前      | 门外实际图像恢复，不拿错标“室内”的标签代判                           |
| 五金店内部      | 384–387匹配75/89/73/88等店内真实来源，388本身仍未决                   |
| 酒吧木廊        | 出店后仍在同木廊范围时有正确匹配                                       |

原先按重复标签得到的7次返回与这8个实际区域不是同一分母，不能把新结果称为在同一评测上从38.52%优化到87.5%。它是**评测单位和视觉裁决的纠正**，并非重新推理提高了算法。

### 8.3 三个明确错对不是预算造成的

| 错对                                | 事后XY距离（源单位） | 两组通过支持      | 预算耗尽 |
| ----------------------------------- | -------------------: | ----------------- | -------- |
| 575→194：加油站外围→当铺临门/内部 |              3923.55 | 66/.524，60/.545  | 否       |
| 633→303：洗衣店外巷→砖店后室      |              7640.77 | 88/.733，142/.643 | 否       |
| 679→640：公园街段→洗衣店外巷      |              1539.03 | 70/.579，68/.482  | 否       |

当前端三例均在室外，历史端194和303涉及室内/门口，640为室外。不能把它们说成全部六端都是室外。

这些图对均实际通过局部几何，不是地点级缓存免检，也不是“阈值差一点”一类显然可修的问题。633→303比例相当高，盲目提高阈值可能先伤害正常返回。

### 8.4 当前几何门禁能保证什么，不能保证什么

实现是`SuperPoint → LightGlue → 每个图对独立基础矩阵RANSAC`，再要求两组方向不同、hash不同、内点≥60且比例≥0.35。

它没有验证：

- 三摄标定外参下共享的旋转/平移；
- 统一三维地图点、真实尺度或绝对位置；
- 多观察轨迹能否共同解释这些匹配；
- 匹配覆盖是否足够分散、是否只是重复纹理/局部平面；
- 观察者实际占据区域是否相同。

所以“两组独立方向通过”并不是完整多摄定位。不同位置看到同一背景，基础矩阵通过甚至可能是合理的几何现象；它仍不认证人站回原地。

原输出只存数量/比例，没存关键点坐标、mask或F矩阵，因此尚不能确定每例到底是哪块重复砖纹、窗格或背景导致。不能把机制推测包装成已完成逐点验证。

### 8.5 可改进，但不宜继续承诺简单修复

点分布、退化检测、时序一致性和统一标定几何都可能改善误接受；更完整视觉定位需要额外标定、地图和尺度信息，不是换一下matcher的同等成本修补。

截至暂停，有理由判断“当前门禁不足”，没有理由证明“所有纯视觉系统都不可能”。工程上应停止无限开发例调参，优先考虑独立位置约束，而不是把失败重新解释成只差最后一个提示词。

## 9. 为什么讨论GPS与室内外分工

### 9.1 室外：把成熟定位和地图放在合适的位置

若当前/历史定位精度足以区分上述真实距离，三组远距离异地候选可在视觉之前排除。地图可给街道、建筑、公园和入口候选，不必由VLM凭图像从零创造所有地理身份。

潜在收益是：减少全历史候选、降低计算与混淆、增加与外观独立的证据，并让地点范围更容易解释。

但不能将“室外有GPS”理解为任意区域都精确：城市峡谷、漂移、延迟、地图误差、道路两侧、相邻入口和高程仍有问题。需要定位时间、坐标系、质量/误差和失效状态，不是只给一个经纬度。

### 9.2 室内：不是继续全世界海选，而是局部问题

可讨论的分工是：室外确认建筑/入口→进入后维护建筑内局部区域/楼层/访问→出门重新外部定位校正。

室内可依赖视觉连续性、运动信息、已知地图或按需要引入的室内定位，但这些都没有在本项目形成完整可靠主链。相似房间、长走廊、楼层变化和累计漂移不会因为知道建筑地址就消失。

### 9.3 不能越过的边界

- 位置接近不等于同一房间、同一层或同一物品。
- 外部定位冲突可否决远地身份，不能独自认证门内外和语义关系。
- GPS失锁时不能用过期位置硬筛掉真实返回。
- 同一移动电梯的内景身份和它所处楼层是不同层级；742/776不能只看高度判成误认。
- 数据集原生坐标只能作明确的oracle/模拟定位实验，不能冒充设备GPS测量。
- 融合定位不意味着删除持续空间判断、短长期分层、原图、来源、修订或问答隔离。

这一方向停留在提案与讨论。没有执行GPS测试，也没有把地图真值注入生产回写已有结果。

## 11. 经验教训与执行反思

### 11.1 应当继续坚持的做法

1. 冻结输入、标准、预算和失败，不因为一次结果不好就删除或改分母。
2. 模型语义与程序事务分工：程序能校验来源/时间/ID/覆盖，不能伪造正确视觉结论。
3. 原图和长期证据保留，短期摘要只是可恢复工作线索，不升级为事实。
4. 真实provider、真实工具循环和SQLite提交必须有至少一条验证，不能只靠mock。
5. 区分事实、当前解释、未决、位置真值、问题/答案和裁判意见。
6. 先诊断瓶颈，再决定加硬件；最终本机加速结果说明此前不能直接归因于4060算力不足。

### 11.2 本阶段明确存在的执行失误

**第一，过早把局部验证当整体能力信号。** 三个已知返回成功、七个指定负对拒绝，只是开发控制。全量出现新错对之后，不能继续以旧控制通过宣称可靠。

**第二，先报速度，后补质量。** 用户要求精确率/召回率时才补全部输出审核，导致“813跑完”容易被误解为识别通过。今后速度和质量应从冻结计划开始一起定义。

**第三，评分单位和错误定义没有一开始稳定。** 标签一致率、目标UUID、逐帧召回、访问事件、独特地点、物理距离和序数总分轮流出现，曾造成严重误读。最终地点级统计也是助手复核，应明确其非独立gold，不能再次包装成唯一最终准确率。

**第四，模拟器与生产输入存在不一致。** 原图换了，旧pair说明/预载ID未同步；raw recall与生产投影不同；图片未在同轮共同交付。这些测试缺陷使部分后端对照不能裁决算法优劣。

**第五，完整ULVN集成预算设计不当。** 把9查询离线诊断方案逐观察塞进40秒批次，轻量139观察15分钟的吞吐警报没有阻止全量启动；quality背压又让原30分钟预期变成70分钟仍半程。应该在扩大前检查渐近工作量和实际每批预算。

**第六，部分历史根因结论下得过早。** 曾把故障归为Pi重放卡住，后续原请求显示是关系引用/观察ID错误；曾把742/776的高度差当跨层错误，原图却表明是同一移动轿厢。保留原结论并追加纠正是必要的，但更应在首次归因时标明不确定。

**第七，停止条件与付费授权执行曾有偏差。** 历史记录明确出现过一次续跑授权后额外付费恢复的失误。用户最新停止决定必须覆盖旧“继续迭代”任务，剩余预算也不是继续跑的授权。

**第八，工作区保存与知识入口滞后。** Git基线、运行快照、README和实际工作区曾不同步；11月11日重要内容仍未提交。提交标签不等于原图/权重/SQLite备份，应把“可复现”和“已安全保存”分开核验。

### 11.3 这不是“只要换一个模型”的问题

模型能力、检索覆盖、证据交付、地点粒度、视觉别名、调度和评分同时影响结果。即使某个更强模型改善看图，也不自动解决任务索引、位置约束、传感器同步、事务恢复或真实用户体验。

另一方面，也不能把所有工程bug都升格成视觉方法理论不可能。应保留两个层次：具体实现缺口可以修；在缺少独立定位和充分几何时，某些身份歧义本来就不能凭局部外观可靠消除。

## 12. 若未来恢复，应该从哪里开始

以下只是暂停后的可选恢复顺序，**不是继续执行授权，也不是新的自动TODO队列**。

### 12.1 第一步应是恢复可审计状态，而不是启动模型

1. 核验Git HEAD、未提交文件、本地run/权重/编译产物和数据清单；先确认备份需求与隐私范围。
2. 选择一个明确的代码入口和受测快照，不混用原Pi v2、新layered runtime和独立脚本。
3. 明确真正产品目标：辅助回忆、最后所见、室内地点记忆还是室外位置；不要同时以所有benchmark定义成功。
4. 将已否定/有混杂的分数保留作历史，不恢复成当前验收成绩。

### 12.2 如果选择定位＋地图路线

- 先明确定位源、时间对齐、误差、失锁、地图许可与粒度。
- 室外使用位置约束候选和地图范围；室内以建筑/入口为锚，不假装有GPS房间级精度。
- 可在已有813输出上做明确的模拟定位诊断，但必须包含有依据的误差/失锁条件，不能把零误差真值叫GPS实测。
- 重点评估错误接受减少多少、真实返回被误筛多少、门内外/楼层剩余歧义，不只看定位成功演示。
- 改架构前按active约束列出原设计/原因、变更、影响和验证，取得明确确认。

### 12.3 如果继续纯视觉研究

- 不再以同样三个开发正例循环调阈值；先固定独立地点实例/边界判定。
- 原图匹配应保存点坐标、内点mask、几何模型和空间覆盖，允许真正点级失败分析。
- 若引入统一多摄/时序几何，明确标定和尺度条件，不能只把两个独立图对改名成多摄定位。
- 保留无匹配≠新地点、当前连续≠永久首锚点可见、候选≠认证等规则。

### 12.4 如果重回生活记忆问答

- 将物品/人物/事件可检索性与空间判断分开，避免昂贵地点比较阻塞短事件记录。
- 优先验证能否找到证据，再看证据到答案；不能用最终回答提示替代未完成的历史定位。
- 保持原15题/37分支门槛，任何新题集另行冻结，不以扩题或换口径抹掉旧失败。
- 真正评估目标用户能否理解和完成低风险任务，不把自动语义分数当作可用性。

### 12.5 暂停期间不应自动做什么

不自动重跑模型、恢复813、扩大数据/题集、训练、采购显卡、部署云端、接入GPS、改架构、推送/发布/移动tag、清理旧库或批量提交整个工作区。保存和恢复应在用户另行决定后进行。

## 暂停结语

这一个多月完成了从演示到可审计研究系统的跨越，留下真实相机链路、连续三摄数据、长期记忆底座、因果工具、完整运行、性能优化和具体失败证据。**并不是没有成果，而是已经看清：工程跑通、描述合理、局部匹配成立，与可靠地知道“我在哪里、是否回来过、该取哪段历史”之间仍有明显距离。**

暂停时应保留的不是一个夸大的成功结论，也不是“纯视觉毫无价值”的反向结论，而是：哪些模块已经可复用，哪些假设被否定，哪些问题需要独立定位/地图/更完整几何或更好的生活记忆组织来解决。

本次按用户决定暂时停止项目。未来若恢复，应从这些证据和边界继续，而不是重新跑同一组小样本直到得到一次好结果。
