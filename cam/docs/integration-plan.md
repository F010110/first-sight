# 后续接入准备（未实施）

> 状态更新：单摄串口→主机→当前Context／SQLite链已实现，见[串口接入实测](./serial-integration.md)。本文下方是接入前设计，三摄Wi-Fi与设备时间同步仍未实施。

## 项目关系

- `web/` 是保留的手机试用前端，尚未全面迁移至当前 Context 循环。
- `sim/` 和 `src/sim/` 承担现有模拟器、回放及评测职责。
- `cam/` 目前只是独立硬件验证，不是新业务入口；没有修改上述模块或 `src/agent/`，也没有添加根目录启动命令。

## 建议边界

把摄像头作为可替换的**图像输入源**，而非直接在 ESP32 上实现现有 Agent。建议未来由主机适配层负责请求采图、完整性检查、解码、时间戳、设备身份、缓存与限流，再按项目实际图像契约送入处理链。接入前必须重新阅读当时的当前接口，不能把旧手机接口或诊断串口协议直接视为正式接口。

当前串口 115200 的有效图像吞吐量有限：约 18 KB 的 JPEG 仅串行传输理论上已需约 1.6 秒（8N1），还不含采集和预热。它是验机途径，不是已验证的视频方案。未来可比较串口、Wi-Fi HTTP 抓拍/流、原生 USB 等方式；后两者均需独立固件与测试，目前没有实现。

## 后续实施前应明确

1. 使用旧手机演示还是当前模拟器/新运行链作为目标，避免两个版本耦合。
2. 采样频率、分辨率、清晰度、延迟、移动使用和电源需求。
3. 主机适配层的输入契约：JPEG/解码图像、尺寸、采集时间与接收时间、序号、设备标识、旋转/镜像状态。
4. 断线、复位、超时、坏帧、重复帧的处理；失败不得生成虚假观察或重复写记忆。
5. 先用固定图像做离线接口测试，再做 CAM 对照测试；不覆盖现有评测证据。
6. 私人图像的存储期限、上传授权、日志脱敏；网络接口的认证和访问范围。
7. 端到端测试中模型调用的费用授权。本次硬件验证没有调用模型。

## 建议验收顺序

先增加低/中/高分辨率和长时间采集测试，再测断线重连、供电与移动图像；随后独立验证主机图像适配器；最后在明确批准后接业务入口。保留模拟器为可复现基线，不以真实摄像头替换已有测试数据。
